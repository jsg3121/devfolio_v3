## 들어가며

> 이 글은 **포케코리아 API 서버 메모리 장애 추적기** 시리즈의 두 번째 글입니다.
>
> 1편 원인 파악 → 2편 대응과 검증

[1편](/articles/poke-korea-memory-1-root-cause)에서는 API 서버가 메모리 한도에 걸려 하루 10~16번 재시작되던 원인을 찾았다. 정리하면 세 가지가 겹쳐 있었다.

- **재시작할 때마다 요청이 실패했다.** Apollo Server가 종료 신호를 받자마자 먼저 멈추는데, HTTP 서버는 keep-alive 연결로 요청을 계속 받고 있었다.
- **웹 서버까지 오는 요청이 무거웠다.** 문서 요청의 80%가 봇이었고, 모든 페이지가 매번 SSR을 다시 실행하며 API를 여러 번 불렀다.
- **캐시 미스 한 번의 비용이 컸다.** Prisma `distinct`가 필요한 양의 수백 배 행을 가져와 엔진 메모리에서 중복을 거르고 있었다.

이번 글에서는 이 문제들을 어떤 순서로, 어떻게 고쳤는지 정리해 보려고 한다. 고친 뒤 정말 효과가 있었는지도 로컬 측정과 배포 후 6일 동안의 지표로 확인했다.

## 1. 무엇부터 고칠까

고칠 것은 많았지만 한 번에 다 바꾸지 않았다. 원인이 분명하고 되돌리기 쉬운 것부터 순서를 정했다.

| 순서 | 대상                | 대응                                  | 이 순서로 한 이유                                                  |
| ---- | ------------------- | ------------------------------------- | ------------------------------------------------------------------ |
| 1    | 재시작 중 요청 실패 | Apollo drain 적용                     | 원인이 확정됐고, 재시작이 계속되는 동안의 피해를 바로 줄일 수 있음 |
| 2    | 봇 요청             | robots.txt + CloudFront Function 차단 | 코드 변경이 작고, 웹·API 부하를 함께 줄임                          |
| 3    | Prisma `distinct`   | `groupBy` + 메모이제이션              | 메모리를 밀어 올리는 직접 원인                                     |
| 4    | 메모리 한도         | 300MB → 400MB                         | 기본 메모리 대비 여유 확보                                         |

반대로 이번에는 손대지 않기로 한 것도 있다. prefetch 방식과 루트 레이아웃의 `headers()` 때문에 생긴 동적 렌더링 구조다. 이유는 8장에서 다룬다.

## 2. 재시작해도 요청이 실패하지 않게

### Apollo가 먼저 멈추지 않게 하기

1편에서 본 것처럼 문제는 종료 순서였다. Apollo Server는 `SIGINT`를 받자마자 멈추는데, HTTP 서버는 그 뒤에도 keep-alive 연결로 요청을 받고 있었다.

Apollo Server에는 이런 상황을 위한 `ApolloServerPluginDrainHttpServer` 플러그인이 있다. `stop()`이 호출되면 새 연결을 막고, 쉬고 있는 연결은 바로 닫고, 처리 중인 요청은 응답을 보낸 뒤 연결을 닫는다. 유예 시간이 지나면 남은 연결을 강제로 정리한다. [Apollo Server — drainHttpServer plugin](https://www.apollographql.com/docs/apollo-server/api/plugin/drain-http-server)

```ts
// graphql/apolloServer.ts
const apolloServer = new ApolloServer({
  schema,
  cache,
  // 기본값(true)이면 Apollo가 신호를 받자마자 스스로 멈춘다.
  stopOnTerminationSignals: false,
  plugins: [
    ApolloServerPluginDrainHttpServer({ httpServer, stopGracePeriodMillis: 3000 }),
    ApolloServerPluginCacheControl({ defaultMaxAge: 60 * 60 * 12 }),
  ],
});
```

drain 플러그인이 소켓을 추적하려면 `listen()` 전에 HTTP 서버가 있어야 해서, Express의 `app.listen()` 대신 `http.createServer(app)`로 서버를 먼저 만들어 넘겼다. 그리고 Apollo 스스로 멈추지 않도록 `stopOnTerminationSignals`를 껐다. 종료 순서는 이제 내 핸들러가 한 번에 관리한다.

```ts
// index.ts
let isShuttingDown = false;

const shutdown = async (signal: string) => {
  // 정리 도중 신호가 다시 와도 한 번만 정리한다.
  if (isShuttingDown) {
    return;
  }
  isShuttingDown = true;

  // drain 유예(3초)가 지나도 끝나지 않을 때를 대비한 강제 종료.
  // PM2 kill_timeout(5초)보다 짧아야 SIGKILL 전에 스스로 끝난다.
  setTimeout(() => process.exit(1), 4500).unref();

  try {
    await apolloServer.stop(); // drain 플러그인이 HTTP 연결 정리까지 마친 뒤 반환된다.
    await PrismaModule.disconnect();
    process.exit(0);
  } catch (error) {
    console.error('정리 실패:', error);
    process.exit(1);
  }
};
```

중복 실행을 막는 플래그에도 이유가 있다. 기존에는 Apollo가 `stop()`을 마친 뒤 같은 신호를 프로세스에 다시 보내서, 종료 핸들러가 두 번 실행되고 있었다.

### 로컬에서 같은 상황 만들기

운영에서 실험할 수는 없어서, 수정 전과 수정 후 빌드를 로컬에서 각각 띄우고 같은 조건을 만들었다. keep-alive 연결 20개로 DB를 조회하는 GraphQL 쿼리를 계속 보내다가 `SIGINT`를 보내는 방식이다. 세 번씩 반복했다.

| 항목               | 수정 전                                         | 수정 후            |
| ------------------ | ----------------------------------------------- | ------------------ |
| 종료 중 500 응답   | 약 3.5만 건 ("received during server shutdown") | **0건**            |
| 종료까지 걸린 시간 | 약 4초 (강제 종료, exit 1)                      | 0.3~0.5초 (exit 0) |
| 종료 핸들러 실행   | 2회                                             | 1회                |

수정 전 빌드에서는 운영 로그에서 본 메시지가 그대로 재현됐다. 수정 후에는 처리 중이던 요청이 모두 응답을 받은 뒤 0.5초 안에 정상 종료됐다.

### 그래도 남는 것

API 서버는 ALB 대상이 하나뿐이다. 그래서 새 프로세스가 뜨는 몇 초 동안 들어오는 요청은 여전히 ELB 502가 된다. 서버가 연결을 닫는 순간 클라이언트가 그 연결로 다음 요청을 보내는 경합도 연결마다 한 건 정도 남는다. 이 부분까지 없애려면 재시작 자체를 줄여야 했다.

## 3. 봇은 어디에서 막을까

### 미들웨어가 아니라 엣지에서

봇을 막는 방법으로 처음 떠오른 건 Next.js 미들웨어였다. 차단 목록을 코드로 관리할 수 있다는 장점이 있다. 하지만 이번 목적은 웹 서버의 부하를 줄이는 것이었고, 미들웨어는 요청이 이미 그 서버에 도착한 뒤에 실행된다.

| 방법                    | 차단 위치                       | 고려한 점                                                                                                     |
| ----------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Next.js 미들웨어        | 요청이 EC2에 도착한 뒤          | 오리진에서는 ALB의 IP가 보여 `X-Forwarded-For`를 파싱해야 함. 403이 CDN 캐시에 남으면 사용자에게 보일 수 있음 |
| **CloudFront Function** | **엣지 (요청이 ALB에 가기 전)** | 이미 기기 판정과 일부 봇 차단에 쓰고 있던 함수. 함수가 만든 응답은 캐시되지 않음                              |
| AWS WAF 요청 수 제한    | 엣지                            | 웹 ACL·규칙·요청 수 요금으로 이 트래픽에서는 월 약 12달러. 줄인 CloudFront 비용과 비슷                        |

403이 캐시에 남을 수 있다는 점은 특히 신경이 쓰였다. 포케코리아는 예전에 기기별 캐시 키 때문에 PC에서 모바일 화면이 보이는 [캐시 오염 문제](/articles/poke-korea-cdn-device-cache-pollution)를 겪은 적이 있다. 엣지에서 함수가 직접 응답하면 이 걱정을 하지 않아도 됐다. [Amazon CloudFront — CloudFront Functions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-functions.html)

### IP보다 UA로

차단 기준은 IP가 아니라 User-Agent로 잡았다. 이번 대상 봇은 UA로 자기를 밝히고 있었고, IP는 너무 많았다. 이틀치 로그에서 `Baiduspider`는 IP 601개, `ExaSearchBot`은 IP 512개를 쓰고 있었다. IP 목록은 금방 낡지만 UA 문자열 하나는 IP가 바뀌어도 그대로다. IP 대역 차단은 UA를 일반 브라우저로 위장하는 크롤러에만 쓰기로 했다.

### robots.txt와 CloudFront Function을 함께

robots.txt를 지키는 크롤러는 요청 자체를 보내지 않으니, 비용도 오리진 부하도 생기지 않는다. 다만 robots.txt는 크롤러가 지켜 주길 바라는 규약이라 강제력이 없다. [RFC 9309 — Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309) 그래서 두 가지를 함께 적용했다.

```ts
// app/robots.ts
const SEO_UNRELATED_AGENTS = ['QlyzeBot', 'SemrushBot', 'Baiduspider', 'ExaSearchBot'];

// rules
{
  userAgent: SEO_UNRELATED_AGENTS,
  disallow: ['/'],
},
```

```js
// CloudFront Function (viewer-request)
var BLOCKED_UA_TOKENS = ['bytespider', 'qlyzebot', 'semrushbot', 'baiduspider', 'exasearchbot'];

for (var t = 0; t < BLOCKED_UA_TOKENS.length; t++) {
  if (userAgent.indexOf(BLOCKED_UA_TOKENS[t]) > -1) {
    return FORBIDDEN; // 403 + cache-control: no-store
  }
}
```

Googlebot, bingbot, 네이버 Yeti, Daum, 애드센스용 Mediapartners-Google, 링크 미리보기 봇은 목록에 넣지 않았다. 요청이 가장 많던 `meta-webindexer`도 허용했다. AI 학습 크롤러는 막고 AI 검색 크롤러는 허용하던 기존 robots 정책과 맞추기 위해서다.

### 실제 요청으로 미리 확인하기

CloudFront Function은 게시하는 즉시 모든 요청에 적용된다. 잘못 막으면 검색 노출이나 광고에 바로 영향이 가기 때문에, 게시 전에 하루치 실제 요청 23.5만 건을 기존 함수와 수정한 함수에 각각 넣어 결과를 비교했다.

판정이 바뀐 요청은 20,056건이었고, 모두 차단 대상 봇이었다. 나머지 21.5만 건은 기존 함수와 결과가 같았다. 게시한 뒤에는 운영 주소에 봇 UA로 직접 요청을 보내 403과 200이 의도대로 나오는지, 같은 경로를 일반 브라우저로 요청했을 때 캐시된 403이 나오지 않는지도 확인했다.

## 4. distinct를 groupBy로 바꾸고 결과를 기억하기

가장 중요한 수정이다. 실제 수정은 백엔드 저장소에서 진행했고, 1편에서 찾은 쿼리 세 개를 각각 다르게 고쳤다.

### 버전 목록은 groupBy로

"기술의 습득 데이터가 있는 버전 목록"은 서로 다른 값 목록이 필요한 쿼리라, `groupBy`로 바꾸기만 하면 됐다. `groupBy`는 SQL `GROUP BY`로 나가서 DB가 묶은 결과만 보내 준다. [Prisma — groupBy](https://www.prisma.io/docs/orm/reference/prisma-client-reference#groupby)

```ts
// 수정 전
const learnable = await prisma.pokemonLearnset.findMany({
  where: { skillId },
  select: { versionGroupId: true },
  distinct: ['versionGroupId'],
});

// 수정 후
const learnable = await prisma.pokemonLearnset.groupBy({
  by: ['versionGroupId'],
  where: { skillId },
});
```

기존 `(skill_id, version_group_id, …)` 인덱스를 그대로 쓸 수 있어서, 기술 하나당 최대 1.2만 행을 받던 쿼리가 수십 행만 받게 됐다.

### 폼 판정 두 개는 기술과 상관이 없다

나머지 두 쿼리는 1편 마지막에 본 것처럼 `GROUP BY`로 바꿔도 DB가 테이블 전체를 읽는 건 그대로였다. 그런데 이 두 값은 기술과 상관이 없다. "폼에 행이 있는가"는 폼에만, "폼이 이 버전에서 가진 습득법"은 폼과 버전에만 달려 있다. 그러니 기술마다 다시 계산할 필요 없이, **한 번 계산해서 기억해 두면** 됐다.

```ts
const memoize = <T>(store: Map<string, MemoEntry<T>>, key: string, loader: () => Promise<T>) => {
  const hit = store.get(key);
  if (hit && hit.expiresAt > Date.now()) {
    return hit.promise;
  }
  const promise = loader();
  store.set(key, { promise, expiresAt: Date.now() + MEMO_TTL_MS });
  // 실패한 조회는 보관하지 않는다. 보관하면 재시작 전까지 판정이 계속 깨진다.
  promise.catch(() => {
    if (store.get(key)?.promise === promise) {
      store.delete(key);
    }
  });
  return promise;
};
```

결과 대신 **Promise를 보관**한 데는 이유가 있다. 서버가 막 뜬 직후에는 여러 요청이 동시에 같은 값을 찾는다. 결과를 보관하면 첫 조회가 끝나기 전에 들어온 요청들이 각자 같은 조회를 다시 보내지만, Promise를 보관하면 모두 같은 조회를 기다린다. 동시 요청 10개에 조회는 1번만 나가는 것을 테스트로 확인했다.

기억해 둔 값은 1일이 지나면 다시 조회한다. 데이터를 적재한 뒤에는 서버를 재시작해 바로 반영하기로 했는데, 기존 쿼리 캐시도 같은 전제로 운영하고 있어서 규칙을 맞췄다.

### 기억할 때는 키와 조회 범위를 맞춰야 한다

여기서 한 가지 함정이 있었다. 기존 쿼리는 "후보 폼"으로 조건을 걸어 조회했다.

```ts
where: {
  formCode: { in: candidateCodes }, // 후보 폼은 기술마다 다르다
  versionGroupId: { in: versionGroupIds },
}
```

후보 폼은 기술마다 다르다. 이 조건을 그대로 둔 채 결과를 "버전 조합"이라는 키로 기억하면, 다른 기술이 같은 버전으로 요청했을 때 **그 기술의 후보 폼이 빠진 결과**를 돌려주게 된다. 응답이 조용히 틀어지는 종류의 버그라 찾기도 어렵다.

그래서 기억하는 쪽은 후보 폼 조건 없이 그 버전의 **전체 폼**을 조회하고, 후보는 메모리에서 골라내도록 했다. 버전 하나의 (폼, 습득법) 쌍은 많아야 657개라 부담이 없었다.

기억하는 키가 사용자 입력으로 끝없이 늘어나지 않는지도 확인했다. 버전 조합은 요청에 담긴 버전 번호에서 만들어지는데, 존재하지 않는 번호면 러닝셋 행이 0건이라 이 함수에 오기 전에 반환된다. 그래서 실제로 있는 버전 조합(29개 이하)만 키가 된다.

### 응답이 그대로인지 확인하기

쿼리를 바꾸면서 가장 걱정한 건 응답이 달라지는 것이었다. 특히 상속 판정은 데이터의 예외가 많은 부분이라, 수정 전과 수정 후 빌드의 응답 JSON 전체를 비교했다. 습득 포켓몬 목록은 마지막 페이지까지 따라가며 비교했다.

| 비교한 시나리오                       | 건수                          |
| ------------------------------------- | ----------------------------- |
| 기술 919개 × 그 기술이 있는 모든 버전 | 포함                          |
| 습득법 필터 (버전 × 습득법 전 조합)   | 포함                          |
| 세대 지정 요청 (1~9세대)              | 30,649건                      |
| DLC로 묶이는 버전 조합                | 6,605건                       |
| 같은 버전을 다른 기술로 연달아 요청   | 한 프로세스에서 순서대로 실행 |
| 일부 습득법만 상속하는 폼             | 487건의 응답에 포함           |
| **전체**                              | **63,518건, 불일치 0건**      |

전체 비교에 걸린 시간도 814초에서 261초로 줄었다. 쿼리가 가벼워진 효과가 검증 과정에서 먼저 보인 셈이다.

## 5. 메모리 한도는 왜 400MB였을까

쿼리를 고치면 메모리가 줄겠지만, 1편에서 본 것처럼 재시작 직후에도 RSS가 170~220MB였다. 300MB 한도와의 여유가 원래 작았기 때문에 한도도 함께 올리기로 했다. 처음에는 450MB를 생각했는데, 배포할 때를 계산해 보고 400MB로 정했다.

| 상황                                   | 서버 메모리 (2GB 기준) |
| -------------------------------------- | ---------------------- |
| 평소                                   | 약 48%                 |
| 배포 빌드 중 (지금까지 최대)           | 86~88%                 |
| 배포 빌드 중 + API가 400MB까지 찬 경우 | 약 96%                 |
| 배포 빌드 중 + API가 450MB까지 찬 경우 | 약 99%                 |

웹 서버의 빌드가 같은 서버에서 돌기 때문에, 배포할 때는 메모리가 이미 90% 가까이 오른다. 이때 메모리가 바닥나면 리눅스의 OOM killer는 가장 큰 프로세스부터 정리하는데, 그게 API가 아니라 웹 서버일 수 있다. API 재시작보다 훨씬 큰 장애가 되니, 평소 여유와 배포 때 위험 사이에서 400MB를 골랐다.

반영할 때도 주의할 점이 있었다. `ecosystem.config.js`를 바꿔도 `pm2 restart`만으로는 새 한도가 적용되지 않는다. 프로세스를 지우고 설정 파일로 다시 띄운 뒤 `pm2 save`까지 해야 재부팅 후에도 새 설정이 유지된다. 반영 후 `pm2 describe`에서 `max memory restart`가 `419430400`(400MB)인 것을 확인했다.

## 6. 로컬에서 먼저 확인한 효과

운영에 반영하기 전에, 1편에서 원인을 재현했던 조건 그대로 수정 전후를 비교했다. 기술 상세 919건과 기술별 습득 포켓몬 919건(캐시 미스)을 차례로 보내고 같은 순서로 한 번 더 반복했다.

| 항목                                    | 수정 전                       | 수정 후                     |
| --------------------------------------- | ----------------------------- | --------------------------- |
| 기술 상세 919건: 네이티브 메모리 증가   | +36MB                         | +8MB                        |
| 기술별 습득 919건: 네이티브 메모리 증가 | +127MB                        | +42MB                       |
| 최대 RSS                                | 316MB                         | **215MB**                   |
| 러닝셋 조회가 DB에서 받은 행            | 약 440만 (`distinct` 2,045회) | **1.3만 (`groupBy` 927회)** |

받는 행이 99% 넘게 줄었고, 네이티브 메모리 증가도 3분의 1로 줄었다. 수정 후에도 습득 목록 구간에서 네이티브 메모리가 42MB 늘어나는데, 같은 경로의 나머지 쿼리 몫으로 보인다.

## 7. 배포 후 6일 동안의 지표

### 재시작과 응답 시간

| 지표 (일별)        | 수정 전 (11/4~11/10) | 수정 후 (11/12~11/16) |
| ------------------ | -------------------- | --------------------- |
| 메모리 한도 재시작 | 5~16회               | **0회 (6일 연속)**    |
| API 5xx            | 10~447건             | **0건**               |
| ELB 502            | 94~453건             | 15~39건               |
| API 평균 응답시간  | 43~60ms              | 23~28ms               |
| 웹 평균 응답시간   | 74~152ms             | 49~84ms               |
| 서버 CPU 평균      | 13.8~18.5%           | 10.2~12.5%            |

트래픽이 비슷하게 몰린 두 날을 비교하면 차이가 더 잘 보인다.

| 날짜            | API 요청 | API 평균 응답 | API 5xx | ELB 502 |
| --------------- | -------- | ------------- | ------- | ------- |
| 11/7 (수정 전)  | 81.2만   | 60ms          | 121건   | 318건   |
| 11/14 (수정 후) | 85.4만   | 23ms          | 0건     | 32건    |

요청이 더 많았던 날에도 응답 시간은 3분의 1 수준이었고 5xx는 없었다.

### 메모리: 400MB가 필요했다

계측 로그로 6일(8,501분)을 보니 RSS 최대값은 322.9MB였다. 300MB를 넘은 시간은 전체의 0.56%인 48분이었다.

수정 전에는 RSS가 315~385MB까지 치솟으면서 1시간에 여러 번 재시작됐으니, 쿼리 수정 효과는 분명했다. 그런데 한도가 300MB 그대로였다면 이 48분 동안 여전히 재시작됐을 것이다. **재시작이 0회가 된 건 쿼리 수정과 한도 상향이 둘 다 필요했기 때문**이었다. 400MB는 임시로 올린 값이 아니라 이 서비스에 필요한 값으로 두기로 했다.

### 봇 차단

차단 전후 하루씩(11/4, 11/16)의 로그를 비교했다.

| 봇                         | 11/4                    | 11/16                   |
| -------------------------- | ----------------------- | ----------------------- |
| `QlyzeBot`                 | 8,818건                 | 5건                     |
| `Baiduspider`              | 3,881건                 | 0건                     |
| `ExaSearchBot`             | 2,205건                 | 1건                     |
| `SemrushBot`               | 5,152건                 | 1,466건 (전부 403)      |
| Googlebot / bingbot / Yeti | 3,939 / 4,805 / 3,033건 | 4,663 / 5,064 / 3,627건 |

세 봇은 robots.txt를 지켜 크롤링을 멈췄고, `SemrushBot`은 robots.txt를 읽으면서도 요청을 보내고 있지만 엣지에서 모두 막히고 있다. 검색 봇은 그대로 통과했다. 웹 서버까지 온 문서 요청은 4.45만 건에서 3.85만 건으로 14% 줄었다.

### DB 송신량과 비용

| 항목                      | 수정 전       | 수정 후              |
| ------------------------- | ------------- | -------------------- |
| DB 컨테이너 송신량 (하루) | 약 35GB       | 약 24.7GB            |
| API 요청 1건당 DB 송신량  | 약 46KB       | 약 38KB              |
| CloudFront 비용 (월)      | 19달러 (10월) | 약 5달러 (11월 예상) |

DB 송신량은 30% 줄었지만, 트래픽 차이를 빼고 요청 1건당으로 보면 16% 감소였다. 러닝셋 쿼리를 고친 효과는 메모리와 응답 시간에서 컸고, DB 전송량의 대부분은 다른 쿼리에서 나오고 있다는 뜻이다.

## 8. 이번에 하지 않은 것

### prefetch 조정은 보류했다

1편에서 본 것처럼 사용자가 누르려 할 때 페이지 전체를 받는 prefetch도 API 호출을 늘리고 있었다. GA4의 사이트 내 이동 수와 CloudFront의 RSC 요청 수를 비교해 보니, 이동 1번당 RSC 요청이 약 4.1건이었다. 미리 받은 요청의 70~75%는 실제 이동으로 이어지지 않고 버려지고 있었다.

그래도 prefetch를 끄면 줄어드는 API 호출은 하루 약 7만 건(약 11%), CloudFront 비용은 한 달 2달러 정도였다. 그 대가로 누르자마자 화면이 뜨는 체감 속도를 잃는다. 효과에 비해 잃는 게 크다고 판단해, 다른 수정을 먼저 적용하고 그 뒤에도 부하가 문제일 때 다시 보기로 했다.

### 모든 페이지가 동적 렌더링인 구조

루트 레이아웃의 `headers()` 때문에 ISR이 동작하지 않는 문제도 이번에는 고치지 않았다. 이걸 고치면 반복 요청이 캐시에서 응답돼 API 호출이 크게 줄 수 있지만, 기기별 렌더링 방식과 캐시 키를 함께 다시 설계해야 하는 큰 작업이다. 별도의 과제로 남겨 두었다.

## 9. 다음 조사에서 바꿀 점

### 변경은 하나씩 배포하기

쿼리 수정과 메모리 한도 상향을 같은 날 배포했다. 둘 다 재시작을 줄이는 변경이라, 재시작 횟수만으로는 어느 쪽 효과인지 나눌 수 없었다. 다행히 계측 로그의 RSS 최대값으로 "쿼리 수정으로 급증이 사라졌고, 남은 여유는 한도 상향이 메웠다"고 판단할 수 있었다. 하지만 이건 계측 로그를 미리 넣어 둔 덕분이었다. 다음에는 효과를 나눠 봐야 하는 변경은 따로 배포하려고 한다.

### 기준선은 배포 전에 남기기

DB 송신량은 배포 전 값을 따로 기록해 두지 못한 채 배포가 끝나 버렸다. 다행히 전날 다른 확인을 하며 찍어 둔 누적값이 있어서 배포 전 하루치를 복원할 수 있었다. 비교하려는 지표는 배포 전에 먼저 기록해 두는 게 순서였다.

### ORM이 보내는 쿼리를 확인하기

이번 원인은 결국 `distinct`가 SQL로 나가지 않는다는 한 가지 사실이었다. ORM 코드는 SQL보다 읽기 쉽지만, 그 코드가 DB에 무엇을 보내는지는 쿼리 로그나 실행 계획을 봐야 알 수 있다. 행이 많은 테이블을 다루는 쿼리는 작성할 때 쿼리 로그를 한 번씩 확인해 보려고 한다.

## 마치며

1편에서는 비용 점검에서 시작해 원인을 찾았고, 2편에서는 그 원인을 순서대로 고쳤다. 재시작 중 실패는 Apollo drain으로, 봇은 엣지 차단으로, 메모리를 밀어 올리던 쿼리는 `groupBy`와 메모이제이션으로 대응했다. 배포 후 6일 동안 메모리 한도 재시작은 한 번도 없었고, API 응답 시간은 절반이 됐다.

돌아보면 원인을 찾는 것만큼 "고친 게 정말 효과가 있었는가"를 확인하는 데도 시간을 많이 썼다. 응답 63,518건을 비교하고, 로컬과 운영에서 메모리를 측정하고, 6일치 지표를 같은 기준으로 다시 봤다. 그 과정에서 쿼리 수정만으로는 부족하고 한도 상향도 필요했다는 사실을 알 수 있었다. 고친 뒤의 확인까지가 대응이라는 걸 이번 작업에서 다시 느꼈다.
