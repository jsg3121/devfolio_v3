## 들어가며

> 이 글은 **포케코리아 API 서버 메모리 장애 추적기** 시리즈의 두 번째 글입니다.
>
> 1편 원인 파악 → 2편 대응과 검증

[1편](/articles/poke-korea-memory-1-root-cause)에서는 API 서버가 메모리 한도를 초과해 하루 최대 16번 재시작되던 원인을 추적했다. 조사 과정에서 확인한 문제는 세 가지였다.

- **재시작 중 요청이 실패했다.** HTTP 연결 정리와 Apollo Server의 종료 처리가 별도로 실행되면서, 종료 중 후속 GraphQL 요청이 실패했다.
- **웹 요청이 API 부하로 이어졌다.** 웹 서버까지 온 문서 요청의 약 80%가 봇 요청이었고, 페이지 단위 ISR도 적용되지 않고 있었다.
- **캐시 미스 한 번의 조회 비용이 컸다.** 당시 Prisma 구성에서 `distinct`는 많은 행을 가져온 뒤 쿼리 엔진 메모리에서 중복을 제거했다.

이 글에서는 문제별 대응과 검증 과정을 정리한다. 로컬에서 응답 동일성과 메모리 변화를 비교하고, 배포 후에는 재시작 횟수와 응답 시간 등 운영 지표를 확인했다.

시각은 모두 한국 시간 기준이다. 메모리 수치는 1편과 같이 기존 로그의 MB 표기를 유지했고, PM2 설정값은 필요한 곳에 바이트와 MiB를 함께 적었다. 코드는 설명에 필요한 부분만 발췌했다.

## 1. 무엇부터 고칠까

고칠 것은 많았지만 한 번에 다 바꾸지 않았다. 원인이 분명하고 되돌리기 쉬운 것부터 순서를 정했다.

| 순서 | 대상                | 대응                                  | 이 순서로 한 이유                                                  |
| ---- | ------------------- | ------------------------------------- | ------------------------------------------------------------------ |
| 1    | 재시작 중 요청 실패 | Apollo drain 적용                     | 원인이 확정됐고, 재시작이 계속되는 동안의 피해를 바로 줄일 수 있음 |
| 2    | 봇 요청             | robots.txt + CloudFront Function 차단 | 코드 변경이 작고, 웹·API 부하를 함께 줄임                          |
| 3    | Prisma `distinct`   | `groupBy` + 메모이제이션              | 로컬에서 RSS 증가가 재현된 대량 행 조회 개선                       |
| 4    | 메모리 한도         | 300MB → 400MB                         | 기본 메모리 대비 여유 확보                                         |

prefetch 방식과 루트 레이아웃의 `headers()`를 사용하는 동적 렌더링 구조는 이번 변경에서 제외했다. 이유는 8장에서 다룬다.

## 2. 종료 중 요청 실패 줄이기

### Apollo가 먼저 멈추지 않게 하기

1편에서 확인한 문제는 종료 처리 순서였다. 당시에는 `SIGINT` 수신 시 Apollo의 `stop()`과 애플리케이션의 HTTP 연결 정리가 별도로 실행됐다. 그 과정에서 기존 keep-alive 연결의 후속 요청이 Apollo의 종료 상태와 겹쳐 실패했다.

Apollo Server의 `ApolloServerPluginDrainHttpServer`는 `stop()` 호출 시 HTTP 연결을 함께 정리한다. 새 연결을 차단하고 유휴 연결을 닫으며, 처리 중인 요청은 응답이 완료돼 연결이 유휴 상태가 되면 닫는다. 유예 시간이 지나도 남아 있는 연결은 강제로 종료한다. [Apollo Server — drainHttpServer plugin](https://www.apollographql.com/docs/apollo-server/api/plugin/drain-http-server)

```ts
// graphql/apolloServer.ts
const apolloServer = new ApolloServer({
  schema,
  cache,
  // 종료 신호는 애플리케이션 핸들러에서 처리한다.
  stopOnTerminationSignals: false,
  plugins: [
    ApolloServerPluginDrainHttpServer({ httpServer, stopGracePeriodMillis: 3000 }),
    ApolloServerPluginCacheControl({ defaultMaxAge: 60 * 60 * 12 }),
  ],
});
```

drain 플러그인이 연결을 추적할 수 있도록, Express의 `app.listen()` 대신 `http.createServer(app)`로 HTTP 서버를 먼저 생성해 전달했다. `stopOnTerminationSignals`도 비활성화하고, 종료 순서를 애플리케이션 핸들러에서 관리하도록 변경했다.

```ts
// index.ts
let isShuttingDown = false;

const shutdown = async (signal: string) => {
  // 정리 도중 신호가 다시 와도 한 번만 정리한다.
  if (isShuttingDown) {
    return;
  }
  isShuttingDown = true;

  // drain 유예(3초)가 지나도 끝나지 않을 때를 대비한 강제 종료.
  // 운영에서 설정한 PM2 kill_timeout(5초)보다 먼저 실행되도록 한다.
  setTimeout(() => process.exit(1), 4500).unref();

  try {
    await apolloServer.stop(); // drain 플러그인이 HTTP 연결 정리까지 마친 뒤 반환된다.
    await PrismaModule.disconnect();
    process.exit(0);
  } catch (error) {
    console.error('정리 실패:', error);
    process.exit(1);
  }
};
```

중복 실행을 막는 플래그에도 이유가 있다. 기존에는 Apollo가 `stop()`을 마친 뒤 같은 신호를 프로세스에 다시 보내서, 종료 핸들러가 두 번 실행되고 있었다.

### 로컬에서 같은 상황 만들기

운영 요청에 영향을 주지 않도록 수정 전후 빌드를 로컬에서 각각 실행했다. keep-alive 연결 20개로 DB를 조회하는 GraphQL 쿼리를 반복해서 보내다가 `SIGINT`를 전달했다. 같은 조건에서 세 번씩 반복했다.

| 항목               | 수정 전                                         | 수정 후            |
| ------------------ | ----------------------------------------------- | ------------------ |
| 종료 중 500 응답   | 약 3.5만 건 ("received during server shutdown") | **0건**            |
| 종료까지 걸린 시간 | 약 4초 (강제 종료, exit 1)                      | 0.3~0.5초 (exit 0) |
| 종료 핸들러 실행   | 2회                                             | 1회                |

수정 전 빌드에서는 운영 로그에서 본 메시지가 그대로 재현됐다. 수정 후에는 처리 중이던 요청이 모두 응답을 받은 뒤 0.5초 안에 정상 종료됐다.

### 그래도 남는 것

API 서버는 ALB 대상이 하나뿐이므로, 프로세스가 재시작되는 동안 요청을 처리할 다른 대상이 없다. 이 구간에는 ALB 502 등 연결 오류가 발생할 수 있다. 서버가 연결을 닫는 시점과 클라이언트가 후속 요청을 보내는 시점의 경합도 남는다. drain 적용으로 종료 중 GraphQL 오류는 줄였지만, 재시작 중의 요청 실패까지 모두 없앤 것은 아니다. 다음으로는 재시작 자체를 줄이는 데 집중했다.

## 3. 봇은 어디에서 막을까

### 미들웨어가 아니라 엣지에서

처음에는 차단 목록을 코드로 관리할 수 있는 Next.js 미들웨어를 검토했다. 다만 이 서비스처럼 EC2에서 직접 호스팅하는 구성에서는 요청이 웹 서버에 도착한 뒤 미들웨어가 실행된다. 오리진 부하를 줄이려면 그보다 앞에서 차단하는 편이 적합했다.

| 방법                    | 차단 위치                       | 고려한 점                                                                                                     |
| ----------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Next.js 미들웨어        | 요청이 EC2에 도착한 뒤          | 오리진에서는 ALB의 IP가 보여 `X-Forwarded-For`를 파싱해야 함. 403이 CDN 캐시에 남으면 사용자에게 보일 수 있음 |
| **CloudFront Function** | **엣지 (요청이 ALB에 가기 전)** | 이미 기기 판정과 일부 봇 차단에 쓰고 있던 함수. 함수가 만든 응답은 캐시되지 않음                              |
| AWS WAF 요청 수 제한    | 엣지                            | 웹 ACL·규칙·요청 수 요금으로 이 트래픽에서는 월 약 12달러. 줄인 CloudFront 비용과 비슷                        |

403이 캐시에 남을 수 있다는 점은 특히 신경이 쓰였다. 포케코리아는 예전에 기기별 캐시 키 때문에 PC에서 모바일 화면이 보이는 [캐시 오염 문제](/articles/poke-korea-cdn-device-cache-pollution)를 겪은 적이 있다. 엣지에서 함수가 직접 응답하면 이 걱정을 하지 않아도 됐다. [Amazon CloudFront — CloudFront Functions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cloudfront-functions.html)

### IP보다 UA로

차단 기준은 User-Agent로 정했다. 대상 봇은 UA로 자신을 식별하고 있었지만, 이틀치 로그에서 `Baiduspider`는 IP 601개, `ExaSearchBot`은 IP 512개를 사용했다. 이 요청들을 관리하는 데는 개별 IP 목록보다 UA 문자열이 적합했다. 다만 UA는 위장할 수 있으므로 봇의 신원을 보장하는 기준은 아니다. 일반 브라우저 UA를 사용하는 크롤러는 별도의 IP 대역 차단 대상으로 검토하기로 했다.

### robots.txt와 CloudFront Function을 함께

robots.txt를 준수하는 크롤러는 금지된 경로의 요청을 줄일 수 있다. 다만 robots.txt 자체를 확인하는 요청은 남고, 이 규약이 접근을 강제로 차단하지는 않는다. [RFC 9309 — Robots Exclusion Protocol](https://www.rfc-editor.org/rfc/rfc9309) 그래서 robots.txt로 크롤링 중단을 요청하고, 계속 들어오는 요청은 CloudFront Function에서 차단했다.

```ts
// app/robots.ts
const SEO_UNRELATED_AGENTS = ['QlyzeBot', 'SemrushBot', 'Baiduspider', 'ExaSearchBot'];

// rules
{
  userAgent: SEO_UNRELATED_AGENTS,
  disallow: ['/'],
},
```

```js
// CloudFront Function (viewer-request)
var BLOCKED_UA_TOKENS = ['bytespider', 'qlyzebot', 'semrushbot', 'baiduspider', 'exasearchbot'];

for (var t = 0; t < BLOCKED_UA_TOKENS.length; t++) {
  if (userAgent.indexOf(BLOCKED_UA_TOKENS[t]) > -1) {
    return FORBIDDEN; // 403 + cache-control: no-store
  }
}
```

Googlebot, bingbot, 네이버 Yeti, Daum, 애드센스용 Mediapartners-Google, 링크 미리보기 봇은 목록에 넣지 않았다. 요청이 가장 많던 `meta-webindexer`도 허용했다. AI 학습 크롤러는 막고 AI 검색 크롤러는 허용하던 기존 robots 정책과 맞추기 위해서다.

### 실제 요청으로 미리 확인하기

기존 CloudFront Function의 새 버전을 게시하면, 배포가 완료된 뒤 해당 함수에 연결된 캐시 동작에서 사용한다. 적용 범위가 넓어 잘못된 차단은 검색 노출이나 광고 요청에 영향을 줄 수 있었다. 게시 전에 하루치 실제 요청 23.5만 건을 기존 함수와 수정한 함수에 각각 입력해 결과를 비교했다. [Amazon CloudFront — Publish functions](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/publish-function.html)

판정이 바뀐 요청은 20,056건이었고, 모두 차단 대상 봇이었다. 나머지 21.5만 건은 기존 함수와 결과가 같았다. 게시한 뒤에는 운영 주소에 봇 UA로 직접 요청을 보내 403과 200이 의도대로 나오는지, 같은 경로를 일반 브라우저로 요청했을 때 캐시된 403이 나오지 않는지도 확인했다.

## 4. groupBy와 메모이제이션으로 조회량 줄이기

메모리 사용량을 줄이기 위한 핵심 변경은 쿼리 수정이었다. 백엔드 저장소에서 1편의 쿼리 세 개를 용도에 맞게 변경했다.

### 버전 목록은 groupBy로

"기술의 습득 데이터가 있는 버전 목록"은 중복 없는 버전 ID 목록이 필요한 쿼리다. 이를 `groupBy`로 변경하면 PostgreSQL에서 SQL `GROUP BY`를 수행하고, 그룹화한 결과만 반환한다. [Prisma — groupBy](https://www.prisma.io/docs/orm/reference/prisma-client-reference#groupby)

```ts
// 수정 전
const learnable = await prisma.pokemonLearnset.findMany({
  where: { skillId },
  select: { versionGroupId: true },
  distinct: ['versionGroupId'],
});

// 수정 후
const learnable = await prisma.pokemonLearnset.groupBy({
  by: ['versionGroupId'],
  where: { skillId },
});
```

기존 `(skill_id, version_group_id, …)` 인덱스를 그대로 쓸 수 있어서, 기술 하나당 최대 1.2만 행을 받던 쿼리가 수십 행만 받게 됐다.

### 폼 판정 두 개는 기술과 상관이 없다

1편의 폼 존재 확인 쿼리는 `GROUP BY`로 바꿔도 실행 계획에 순차 스캔이 남았다. 반환 행 수를 줄이는 것과 별개로 반복 조회도 줄일 필요가 있었다. 나머지 두 판정은 기술 ID에 의존하지 않는다. "폼에 행이 있는가"는 폼에만, "폼이 이 버전에서 가진 습득법"은 폼과 버전에만 의존하므로, 결과를 메모이제이션해 여러 기술 조회에서 재사용하도록 했다.

```ts
const memoize = <T>(store: Map<string, MemoEntry<T>>, key: string, loader: () => Promise<T>) => {
  const hit = store.get(key);
  if (hit && hit.expiresAt > Date.now()) {
    return hit.promise;
  }
  const promise = loader();
  store.set(key, { promise, expiresAt: Date.now() + MEMO_TTL_MS });
  // 실패한 Promise가 TTL 만료 전까지 재사용되지 않도록 제거한다.
  promise.catch(() => {
    if (store.get(key)?.promise === promise) {
      store.delete(key);
    }
  });
  return promise;
};
```

완료된 결과 대신 **Promise를 보관**하면 진행 중인 조회도 공유할 수 있다. 서버 시작 직후 여러 요청이 같은 키를 조회하더라도, 첫 조회가 끝날 때까지 같은 Promise를 기다린다. 동시 요청 10개에서 DB 조회가 한 번만 실행되는 것을 테스트로 확인했다.

TTL은 1일로 설정했고, 만료 후 같은 키의 요청이 들어오면 다시 조회한다. 데이터를 적재한 뒤에는 서버를 재시작해 즉시 반영하기로 했다. 기존 쿼리 캐시도 같은 방식으로 운영하고 있어 무효화 규칙을 맞췄다.

### 캐시 키와 조회 범위 맞추기

메모이제이션을 적용할 때는 조회 범위도 변경해야 했다. 기존 쿼리는 기술별 "후보 폼"으로 범위를 제한하고 있었다.

```ts
where: {
  formCode: { in: candidateCodes }, // 후보 폼은 기술마다 다르다
  versionGroupId: { in: versionGroupIds },
}
```

후보 폼은 기술마다 다르다. 이 조건을 유지한 채 버전 조합만 캐시 키로 사용하면, 다른 기술을 조회할 때 **필요한 후보 폼이 빠진 결과**를 재사용할 수 있다. 요청 자체는 성공하더라도 잘못된 데이터를 반환하는 문제다.

그래서 캐시에는 후보 폼 조건 없이 해당 버전의 **전체 폼**을 조회한 결과를 저장하고, 요청별 후보는 메모리에서 필터링하도록 했다. 버전 하나의 (폼, 습득법) 쌍은 최대 657개였다.

캐시 키는 요청의 버전 번호에서 파생된 버전 조합으로 구성한다. 러닝셋 행이 없는 요청은 이 함수에 도달하기 전에 반환되므로, 그런 요청의 캐시 항목은 생성되지 않는다. 다만 이 조건만으로 전체 키 개수의 상한이 보장되는 것은 아니다. 같은 조합이 여러 키로 저장되지 않도록 정렬·중복 제거 기준을 맞추고, 허용하는 조합의 범위도 구분해야 한다. 위 예제의 Map에는 별도의 항목 수 제한이나 만료 항목 일괄 삭제가 없으므로, 입력 조합을 자유롭게 허용하는 용도에 그대로 적용해서는 안 된다.

### 응답이 그대로인지 확인하기

쿼리 변경 후에는 기존 응답이 유지되는지 확인했다. 특히 상속 판정은 데이터의 예외가 많은 부분이라, 수정 전후 빌드의 응답 JSON 전체를 비교했다. 습득 포켓몬 목록은 마지막 페이지까지 조회하며 비교했다.

| 비교한 시나리오                       | 검증 범위와 건수              |
| ------------------------------------- | ----------------------------- |
| 기술 919개 × 그 기술이 있는 모든 버전 | 포함                          |
| 습득법 필터 (버전 × 습득법 전 조합)   | 포함                          |
| 세대 지정 요청 (1~9세대)              | 30,649건                      |

전체 비교에 걸린 시간도 814초에서 261초로 줄었다. 응답 동일성을 확인하는 과정에서 조회 시간 감소도 관측됐다.

## 5. 메모리 한도는 왜 400MB였을까

쿼리를 고치면 메모리가 줄겠지만, 1편에서 본 것처럼 재시작 직후에도 RSS가 170~220MB였다. 300MB 한도와의 여유가 원래 작았기 때문에 한도도 함께 올리기로 했다. 처음에는 450MB를 생각했는데, 배포할 때를 계산해 보고 400MB로 정했다.

| 상황                                     | 서버 메모리 사용률 (2GB 기준) |
| ---------------------------------------- | ----------------------------- |
| 평소                                     | 약 48%                        |
| 배포 빌드 중 (지금까지 최대)             | 86~88%                        |
| 배포 빌드 중 + API가 400MB에 도달한 경우 | 약 96% (추정)                 |
| 배포 빌드 중 + API가 450MB에 도달한 경우 | 약 99% (추정)                 |

웹 서버 빌드도 같은 인스턴스에서 실행돼, 배포 중 메모리 사용률이 90% 가까이 올라간 기록이 있었다. OOM이 발생하면 Linux는 메모리 사용량과 `oom_score_adj` 등이 반영된 점수로 종료 대상을 선택한다. API뿐 아니라 웹 서버가 종료될 가능성도 고려해야 했다. [Linux — OOM killer score](https://www.kernel.org/doc/html/latest/filesystems/proc.html#proc-pid-oom-adj-proc-pid-oom-score-adj-adjust-the-oom-killer-score)

평소 API 메모리의 여유와 배포 중 서버 전체 사용량을 함께 고려해 400MB를 선택했다. 다만 PM2의 메모리 기준은 기본적으로 30초마다 확인하는 재시작 조건이므로, 그 사이 RSS가 더 증가할 수 있다. 이 값이 서버 전체의 OOM을 방지하는 상한을 보장하지는 않는다.

설정 반영 방식도 구분해야 한다. 프로세스 이름만 지정한 재시작과 `pm2 restart ecosystem.config.js`처럼 변경한 설정 파일을 지정한 재시작은 다르다. 이번에는 프로세스를 삭제한 뒤 설정 파일로 다시 등록했지만, 프로세스 삭제가 항상 필요한 절차는 아니다. 반영 후 `pm2 describe`에서 `max memory restart`가 `419430400`바이트(400MiB)인지 확인하고, `pm2 save`로 복원할 프로세스 목록을 저장했다. [PM2 — Ecosystem File](https://pm2.keymetrics.io/docs/usage/application-declaration/)

## 6. 로컬에서 먼저 확인한 효과

운영 반영 전에 1편과 같은 요청 시나리오로 수정 전후를 비교했다. 기술 상세 919건과 기술별 습득 포켓몬 919건(캐시 미스)을 차례로 보내고, 같은 순서로 한 번 더 반복했다. 아래 수치는 이번 비교 실행에서 측정한 값이다. 차감값은 `rss − heapTotal − external`이며, 1편과 같이 네이티브 메모리의 직접 측정값이 아닌 보조 지표로 사용했다.

| 항목                                  | 수정 전                       | 수정 후                     |
| ------------------------------------- | ----------------------------- | --------------------------- |
| 기술 상세 919건: 차감값 변화 (추정)   | +36MB                         | +8MB                        |
| 기술별 습득 919건: 차감값 변화 (추정) | +127MB                        | +42MB                       |
| 최대 RSS                              | 316MB                         | **215MB**                   |
| 러닝셋 조회가 DB에서 받은 행          | 약 440만 (`distinct` 2,045회) | **1.3만 (`groupBy` 927회)** |

DB에서 반환받는 행 수는 99% 이상 줄었고, 최대 RSS는 316MB에서 215MB로 낮아졌다. 습득 목록 구간의 차감값 증가도 127MB에서 42MB로 줄었다. 수정 후에도 RSS 증가가 남았지만, 이 지표만으로 나머지 쿼리나 메모리 할당자의 영향을 분리할 수는 없다.

수정 후에도 로그상 300MB를 초과한 표본이 남아 있어, 기존 기준의 여유가 충분하다고 보기는 어려웠다. 다만 PM2의 점검 시점과 계측 시점이 다르고 두 변경을 함께 배포했으므로, 기존 한도에서 몇 번 재시작됐을지는 알 수 없다. 관측된 RSS와 배포 시 메모리 사용량을 바탕으로 400MB 설정을 유지하기로 했다. 이는 필수 메모리 용량을 입증한 값이 아니라 당시 운영 조건을 고려해 선택한 재시작 기준이다.

## 8. 이번에 하지 않은 것

### prefetch 조정은 보류했다

1편에서 확인한 prefetch 방식도 API 부하에 영향을 줄 수 있어 추가 조정을 검토했다. GA4의 사이트 내 이동 수로 CloudFront의 RSC 요청 수를 나누면 약 4.1이었다. 다만 GA4 이동 이벤트와 RSC 요청은 집계 대상이 같지 않고, 이 비교에는 개별 prefetch 결과가 실제 이동에 사용됐는지에 대한 정보가 없다. 따라서 이 비율을 사용되지 않은 prefetch의 비율로 해석할 수는 없다.

당시 요청량과 회귀 추정치를 바탕으로 계산한 prefetch 비활성화의 절감 규모는 API 호출 하루 약 7만 건(약 11%), CloudFront 비용 월 약 2달러였다. 이는 비활성화 실험으로 검증한 값은 아니다. 페이지 이동 지연이 늘어날 가능성도 있어, 먼저 쿼리와 종료 처리를 수정하고 이후에도 부하가 문제가 되면 prefetch를 별도로 비교하기로 했다.

### 모든 페이지가 동적 렌더링인 구조

루트 레이아웃의 `headers()` 사용으로 페이지 단위 ISR이 적용되지 않는 구조도 이번에는 변경하지 않았다. 렌더링 결과를 재사용하면 반복 요청의 부하를 줄일 수 있지만, 기기별 렌더링과 캐시 키를 함께 설계해야 한다. 동적 렌더링을 유지하면서 Data Cache를 활용하는 방법도 검토할 수 있어, 별도의 과제로 남겼다. [Next.js 15 — Caching](https://nextjs.org/docs/15/app/guides/caching)

## 9. 다음 조사에서 바꿀 점

### 변경은 하나씩 배포하기

쿼리 수정과 메모리 한도 상향을 같은 날 배포했다. 둘 다 재시작 횟수에 영향을 주는 변경이라, 운영 지표만으로 각 효과를 분리하기 어려웠다. 로컬 비교에서는 쿼리 수정 후 최대 RSS가 낮아졌고, 운영 계측에서는 기존 기준 부근의 메모리 사용이 남아 있었다. 두 결과는 판단 근거가 되지만, 각 변경의 독립적인 운영 효과를 증명하지는 않는다. 다음에는 장애 영향이 허용하는 범위에서 변경을 나눠 적용하고 비교할 기간을 확보하려고 한다.

### 기준선은 배포 전에 남기기

DB 송신량은 배포 전에 기준값을 따로 남기지 못했다. 전날 기록해 둔 누적값으로 배포 전 하루치를 복원할 수 있었지만, 처음부터 비교 구간을 정했다면 해석이 더 명확했을 것이다. 다음에는 배포 전에 지표의 집계 범위와 측정 간격도 함께 기록하려고 한다.

### ORM이 보내는 쿼리를 확인하기

이번 조사에서는 당시 Prisma 구성의 `distinct`가 SQL의 중복 제거로 처리되지 않는다는 점이 중요했다. ORM 코드만으로는 실제 조회량과 실행 방식을 알기 어려웠다. 행이 많은 테이블의 쿼리는 실행 SQL과 실행 계획, 반환 행 수를 함께 확인하려고 한다.

## 마치며

1편에서는 비용 점검에서 시작해 재시작의 원인을 추적했고, 2편에서는 문제별 대응과 검증 과정을 정리했다. Apollo drain으로 종료 처리를 개선하고, 엣지에서 봇 요청을 차단하고, `groupBy`와 메모이제이션으로 조회량을 줄였다. 메모리 한도도 함께 조정했다. 수정 후 11월 12~16일에는 메모리 한도 재시작이 0회였고, 일평균 API 응답 시간은 43~60ms에서 23~28ms로 낮아졌다.

원인 수정 이후에는 응답 63,518건을 비교하고, 로컬과 운영에서 메모리를 측정하고, 운영 지표를 다시 확인했다. 쿼리 개선으로 줄어든 조회량과 RSS, 기존 메모리 기준의 여유를 각각 살펴볼 수 있었다. 동시에 여러 변경을 함께 적용하면 효과를 분리하기 어렵다는 한계도 남았다. 다음 대응에서는 기준선을 먼저 기록하고, 확인한 사실과 추정을 구분해 검증 과정을 남기려 한다.
