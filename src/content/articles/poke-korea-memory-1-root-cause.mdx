## 들어가며

> 이 글은 **포케코리아 API 서버 메모리 장애 추적기** 시리즈의 첫 번째 글입니다.
>
> 1편 원인 파악 → 2편 대응과 검증

11월 초에 포케코리아의 CloudFront 비용을 줄이는 작업을 했다. Next.js `<Link>`가 화면에 보이는 링크를 미리 가져오는 prefetch로 요청이 많이 발생하고 있었다. 이를 사용자 상호작용 시점에 prefetch를 실행하는 방식으로 변경했다. 약 일주일 뒤, 실제로 비용이 줄었는지 확인했다.

CloudFront 비용은 줄어 있었지만, 요청 수와 메모리 지표에서는 다른 변화가 보였다. 웹 서버로 가는 요청은 절반으로 줄었는데 API 요청은 오히려 늘었고, 서버 메모리 사용률도 상승하고 있었다. 프로세스 기록을 확인하니 API 서버가 메모리 한도를 초과해 **하루 최대 16번 재시작**되고 있었다.

이 글은 재시작의 원인을 추적한 기록이다. 조사 중 세웠다가 배제한 가설과 그 판단 근거도 함께 정리했다. 원인을 수정하고 효과를 검증한 과정은 2편에서 다룬다.

시각은 모두 한국 시간 기준이다. 코드는 설명에 필요 없는 부분을 덜어 냈다.

## 1. 운영 환경

[지난 장애](/articles/poke-korea-cpu-credit-exhaustion) 이후 인스턴스를 t3.small로 바꿨고, 구성은 그대로다. 서버 한 대에 모든 프로세스가 올라가 있다.

```
CloudFront (웹, 이미지)
  │
  ▼
ALB
  ├─ 웹       → :80    Next.js (App Router)
  ├─ API      → :4000  Apollo Server + Prisma
  └─ 블로그   → :3001  Docusaurus
  │
  ▼
EC2 t3.small (2 vCPU / 2GB)
  ├─ PM2로 웹·API·블로그 프로세스 실행
  └─ Docker PostgreSQL
```

지난 장애와 비교하면 두 가지가 달라졌다.

- **API 도메인이 CloudFront를 거치지 않는다.** 비용 절감 작업 중 11월 2일에 API 도메인을 ALB로 바로 연결했다. 당시 API 배포에서는 응답 캐시와 WAF를 사용하지 않아, 요청 비용을 줄이기 위해 CloudFront를 제외했다.
- **API 서버에 graceful shutdown이 있다.** 지난 장애 때 추가했다. 종료 신호를 받으면 `server.close()`로 연결을 정리하고, 4초 안에 끝나지 않으면 강제 종료한다.

## 2. 비용은 정말 줄고 있었을까

### 하루 금액만 보면 착시가 생긴다

Cost Explorer에서 확인한 CloudFront 일별 비용은 10월 말 하루 약 1.2달러에서 11월 초 약 0.05달러로 줄어 있었다.

그런데 10월 초의 금액을 같이 보니 이상한 점이 있었다.

| 기간        | 하루 금액     |
| ----------- | ------------- |
| 10/1~10/18  | 0.16~0.22달러 |
| 10/19~10/31 | 1.08~1.43달러 |
| 11/1 이후   | 0.05~0.08달러 |

같은 10월인데 19일을 기준으로 금액이 약 6배로 늘었다. 당시 사용하던 CloudFront 요금제에는 월 요청 1,000만 건의 무료 한도가 있었고, 이 서비스의 비용은 대부분 요청 수 과금에서 발생했다. 10월 19일에 무료 한도를 소진하면서 비용이 늘었고, 11월 1일에는 월 한도가 초기화되면서 다시 줄었다. [Amazon CloudFront — 요금](https://aws.amazon.com/cloudfront/pricing/)

11월 초의 낮은 비용에는 무료 한도 초기화의 영향이 섞여 있었다. 작업 효과를 구분하려면 **요청 수**도 함께 비교해야 했다.

### 요청 수로 다시 보기

CloudWatch의 CloudFront `Requests` 지표로 하루 평균을 비교했다.

| 배포          | 10/20~10/31 | 11/4~11/9     | 변화     |
| ------------- | ----------- | ------------- | -------- |
| 웹            | 44.4만      | 25.4만        | −43%     |
| API           | 약 40만     | 0             | −100%    |
| 이미지        | 11.8만      | 12.6만        | +7%      |
| **계정 전체** | **약 99만** | **약 38.5만** | **−61%** |

CloudFront 전체 요청 수는 약 61% 줄었다. 웹 요청 감소와 API 도메인의 경로 변경이 반영된 결과였다. 이미지 요청은 오히려 7% 늘었지만, 이 수치만으로 사용자 수의 증감을 판단할 수는 없다. 여기서 확인한 것은 CloudFront에서 처리하는 요청 수가 줄었다는 점이다.

## 3. 웹은 줄었는데 API는 늘었다

이상한 건 CloudFront 뒤쪽이었다. ALB 지표를 대상 그룹별로 나눠 보니 웹과 API가 반대로 움직이고 있었다.

| ALB 대상 그룹 (하루)     | 10/25~11/1 | 11/4~11/9 |
| ------------------------ | ---------- | --------- |
| 웹 요청                  | 약 26만    | 약 12.8만 |
| API 요청                 | 약 39만    | 60만~81만 |
| API 요청 수 / 웹 요청 수 | 1.6        | 5.2       |
| 웹 평균 응답 시간        | 22~38ms    | 74~114ms  |
| API 평균 응답 시간       | 20~24ms    | 43~60ms   |

웹 요청은 절반으로 줄었지만 API 요청은 약 1.5~2배로 늘었다. 평균 응답 시간도 웹과 API 모두 증가했다. 같은 기간 서버의 일평균 메모리 사용률은 47%에서 68%까지 상승했다. 표의 요청 수 비율은 두 대상 그룹의 집계값을 나눈 값이며, 개별 웹 요청의 API 호출 횟수를 추적한 결과는 아니다.

먼저 API 도메인을 ALB로 직접 연결한 영향을 의심했다. 기존 API용 CloudFront 배포는 캐시가 꺼져 있었고(`Managed-CachingDisabled`), WAF나 응답 헤더 정책도 없었다. 따라서 캐시 제거로 오리진 요청이 증가했다는 설명은 맞지 않았다. 다른 원인을 찾기 위해 웹 요청의 구성을 확인했다.

## 4. 액세스 로그로 범위 좁히기

CloudFront 액세스 로그는 S3에 쌓이고 있어서, 작업 전후의 같은 요일(10월 28일, 11월 4일)을 하루씩 받아 비교했다.

### 웹 요청 하나가 API를 몇 번 부를까

CloudFront 캐시 미스로 웹 서버까지 전달된 요청을 RSC 요청과 문서 요청으로 나누고, 시간대별 ALB API 요청 수와 비교했다. 두 요청 유형이 API 부하와 어떤 관계가 있는지 보기 위해 `API 요청 수 ≈ RSC 요청 수 × a + 문서 요청 수 × b` 형태의 회귀 모형을 사용했다.

| 요청 유형별 회귀계수 (API 요청 수 / 웹 요청 수) | 10/28  | 11/4   |
| ----------------------------------------------- | ------ | ------ |
| RSC 요청                                        | 약 0   | 약 2   |
| 문서 요청                                       | 약 7.7 | 약 7.8 |

각 날짜의 시간대별 표본 24개로 추정한 값이다. 이 모형은 API 요청을 두 유형의 웹 요청으로 설명한다는 가정을 둔다. 직접 API 호출이나 다른 요청 유형, 두 변수 사이의 상관관계가 계수에 영향을 줄 수 있으므로, 실제 요청 한 건의 API 호출 횟수로 해석하기는 어렵다. 추가로 조사할 요청 유형을 고르는 단서로 볼 수 있다.

RSC 요청의 회귀계수가 커진 시점은 prefetch 변경 시점과 겹쳤다. 기존 방식은 동적 경로의 로딩 경계까지 가져왔지만, 변경한 방식은 사용자 상호작용 시점에 `router.prefetch()`를 호출했다. 당시 프로젝트에서 사용한 Next.js 15 구현은 기본 prefetch 종류가 `FULL`이어서, 로딩 경계 이후 페이지 데이터까지 요청할 수 있었다. 요청 수가 줄어도 요청당 데이터 조회량은 늘어날 수 있는 변경이었다. [Next.js 15 — App Router 구현](https://github.com/vercel/next.js/blob/v15.0.0/packages/next/src/client/components/app-router.tsx)

### 웹 서버까지 오는 문서 요청의 80%가 봇이었다

회귀 결과에서 문서 요청의 API 부하 기여도가 크게 추정돼, 문서 요청을 User-Agent별로 나눠 봤다.

| UA (11/4)         | 웹 서버까지 온 문서 요청 | 검색·광고 관련성          |
| ----------------- | ------------------------ | ------------------------- |
| `meta-webindexer` | 7,154                    | Meta AI 검색              |
| `QlyzeBot`        | 6,668                    | 없음                      |
| `SemrushBot`      | 4,638                    | 없음 (SEO 분석 도구)      |
| `Baiduspider`     | 3,175                    | 한국어 서비스라 거의 없음 |
| `ExaSearchBot`    | 2,083                    | 낮음                      |

User-Agent 기준으로 분류했을 때, 웹 서버까지 온 문서 요청의 약 80%가 봇 요청이었다. 특히 `QlyzeBot`은 IP 하나로 한 시간 동안 6,668페이지를 요청했고, 같은 시간대 API 요청은 평소의 약 3배로 증가했다.

### 페이지 단위 ISR이 적용되지 않고 있었다

문서 요청과 함께 API 부하가 증가하는 이유를 확인하려면 렌더링 방식도 살펴봐야 했다. 상세 페이지 대부분에 `revalidate = 31536000`을 설정해 두었기 때문에, 렌더링 결과가 캐시되고 재검증 전까지 재사용될 것으로 예상했다.

그런데 빌드 결과의 `prerender-manifest.json`을 열어 보니 ISR로 잡힌 경로가 하나도 없었다. 정적으로 만들어진 건 `robots.txt`, `sitemap.xml`, `manifest.webmanifest` 세 개뿐이었다.

```tsx
// app/layout.tsx
export default async function RootLayout({ children }: RootLayoutProps) {
  const headersList = await headers();
  const userAgent = headersList.get('user-agent') || '';
  const isMobile = detectUserAgent(userAgent);
  // ...
}
```

루트 레이아웃에서 기기를 판별하기 위해 `headers()`를 사용하고 있었다. 당시 Next.js 구성에서는 이 동적 API를 사용하는 경로가 Full Route Cache에서 제외된다. 루트 레이아웃을 공유하는 페이지에 기대했던 페이지 단위 ISR이 적용되지 않았고, CloudFront 캐시 미스로 도달한 요청마다 서버 렌더링이 수행되고 있었다. [Next.js 15 — Caching](https://nextjs.org/docs/15/app/guides/caching)

다만 동적 렌더링에서도 Data Cache는 사용할 수 있다. SSR이 실행된다는 사실만으로 모든 API 조회가 반복된다고 결론 내릴 수는 없다. 여기서는 페이지 렌더링 결과가 재사용되지 않는다는 점을 확인했고, API 호출량은 앞서 확인한 지표와 함께 판단했다.

봇과 prefetch가 만드는 요청, 페이지 렌더링 결과가 캐시되지 않는 구조가 API 부하와 연결돼 있었다. 다음으로는 이 부하가 프로세스 재시작으로 이어지는 이유를 확인했다.

## 5. API 서버는 왜 재시작되고 있었나

API 요청이 늘어난 이유는 어느 정도 보였다. 그런데 요청이 늘었다고 서버가 재시작되는 건 별개의 문제다. 서버에 들어가 프로세스 상태를 확인했다.

### 크래시가 아니라 메모리 한도였다

`pm2 list`에서 API 프로세스의 재시작 횟수는 79였고, 가동 시간은 28분이었다. 크래시 반복(`unstable restarts`)은 0이었고 `dmesg`에도 OOM 흔적이 없었다. 원인은 `pm2.log`에 그대로 남아 있었다.

```
PM2 log: [PM2][WORKER] Process 5 restarted because it exceeds --max-memory-restart value
  (current_memory=316215296 max_memory_limit=314572800 [octets])
```

PM2의 `max_memory_restart` 설정은 `300M`이었다. 이는 로그의 `314572800`바이트, 즉 300MiB에 해당한다. PM2가 주기적으로 RSS를 확인하면서 기준 초과를 감지하면 프로세스를 재시작하고 있었다. 이 설정은 메모리 할당 자체를 막는 상한은 아니다. [PM2 — Max Memory Threshold Auto Reload](https://pm2.keymetrics.io/docs/usage/memory-limit/) 하루 동안의 재시작 간격은 짧게는 9분이었다.

이하 본문에서는 기존 운영 기록의 명칭에 맞춰 이를 300MB 한도로 부른다. 계측 표의 MB 수치도 원래 로그 표기를 유지했다.

### 재시작할 때마다 요청이 실패하고 있었다

재시작 과정에서는 요청 실패도 발생하고 있었다. API 서버의 오류 로그에는 같은 메시지가 수천 줄 남아 있었다.

```
A GraphQL operation was received during server shutdown. The operation will fail.
Consider draining the HTTP server on shutdown
정리 시간 초과. 강제 종료
```

ALB 지표로 봐도 API 5xx는 11월 3일까지 하루 0~6건이었다가 11월 4일부터 하루 67~447건이 됐다. ELB 502도 하루 13~107건에서 94~453건으로 늘었다.

graceful shutdown을 구현했는데도 요청이 실패한 이유는 종료 처리 순서에 있었다. Apollo Server의 `stopOnTerminationSignals`가 활성화돼 있으면 `SIGINT`를 받았을 때 자체적으로 `stop()`을 호출한다. 당시에는 HTTP 연결을 정리하는 핸들러와 Apollo의 종료 처리가 별도로 실행되고 있었다. [Apollo Server — stopOnTerminationSignals](https://www.apollographql.com/docs/apollo-server/api/apollo-server#stoponterminationsignals)

```text
SIGINT 수신
  ├─ Apollo: 자체 stop() 호출
  └─ 애플리케이션 핸들러: server.close() 호출
        ↓
당시 환경에서 연결 정리 중 후속 GraphQL 요청이 관측됨
  → Apollo의 종료 상태와 겹쳐 HTTP 500 발생
  → 종료 처리가 완료되지 않아 4초 뒤 강제 종료 (exit 1)
```

`server.close()`의 연결 정리 동작은 Node.js 버전에 따라 다르다. Node.js 19부터는 호출 시 유휴 연결도 닫으므로, 새 연결만 차단한다고 설명할 수는 없다. 다만 당시 환경에서는 기존 keep-alive 연결의 후속 요청과 종료 처리가 겹쳤고, Apollo의 종료 상태에서 HTTP 500이 반복됐다. HTTP 연결 정리와 Apollo 종료의 순서를 함께 관리해야 했다. [Node.js — server.close()](https://nodejs.org/api/http.html#serverclosecallback)

이 부분은 원인이 분명해서 먼저 고쳤다. 고친 방법은 2편에서 다룬다. 다만 이건 재시작할 때의 피해를 줄이는 일이고, 재시작 자체는 그대로였다. 메모리가 왜 300MB를 넘는지를 찾아야 했다.

## 6. 메모리는 어디서 늘어나고 있었나

### 처음에는 캐시를 의심했다

API 서버에는 쿼리 결과를 담는 LRU 캐시가 있다. 상한은 64MB인데, 이 크기를 `JSON.stringify` 결과의 바이트 수로 계산하고 있었다. 캐시에 실제로 들어 있는 건 문자열이 아니라 JS 객체이고, 같은 데이터라도 객체는 힙에서 JSON 문자열보다 크게 잡힐 수 있다. 그렇다면 "64MB 상한"이 실제로는 200~300MB가 될 수도 있겠다고 생각했다.

상한을 변경하기 전에 원인을 확인하기 위해, 1분마다 메모리와 캐시 크기를 기록하는 계측 로그를 추가했다.

```ts
const reportMemory = () => {
  const { rss, heapTotal, heapUsed, external } = process.memoryUsage();
  const cache = getQueryCacheStats();

  console.log(
    `[memory] ${JSON.stringify({
      at: new Date().toISOString(),
      rssMB: toMB(rss),
      heapTotalMB: toMB(heapTotal),
      heapUsedMB: toMB(heapUsed),
      externalMB: toMB(external),
      cacheMB: cache.usedMB,
      cacheEntries: cache.size,
    })}`,
  );
};
```

하루치 로그를 받아 보니 예상과 전혀 달랐다.

| 값                       | 범위                                 |
| ------------------------ | ------------------------------------ |
| `heapUsed` / `heapTotal` | 27~88MB / 47~108MB                   |
| 캐시 크기                | 1.8~18MB (항목 수는 거의 항상 2,000) |
| `rss`                    | 169~283MB, 재시작 직전 315~385MB     |

캐시의 직렬화 크기는 64MB 상한보다 작았고, 항목 수가 대부분 2,000개 제한에 도달해 있었다. JS 힙도 RSS와 같은 증가 양상을 보이지 않았다. 캐시 객체가 차지하는 메모리가 없다는 뜻은 아니지만, RSS 증가를 설명하는 주된 가설에서는 제외했다.

### JS 힙 증가만으로 설명되지 않는 RSS

조사 과정에서는 `rss − heapTotal − external`도 보조 지표로 계산했다. 이 차감값은 120~200MB였다. 다만 RSS는 실제 상주 메모리이고, `heapTotal`과 `external`은 각각 다른 기준으로 집계되므로 차감값을 정확한 네이티브 메모리 사용량으로 볼 수는 없다. Node.js 문서도 메모리 할당자의 단편화로 힙 크기가 안정적인 상태에서 RSS가 증가할 수 있다고 설명한다. [Node.js — process.memoryUsage()](https://nodejs.org/api/process.html#processmemoryusage)

다음으로 의심한 것은 Prisma 쿼리 엔진이었다. 이 프로젝트의 Prisma 5는 Rust로 작성된 네이티브 라이브러리(`libquery_engine*.node`)를 Node.js 프로세스 내부에서 사용했다. 엔진이 조회 결과를 처리하면서 사용하는 메모리는 JS 힙 지표만으로 파악하기 어렵다. 차감값만으로 원인을 특정할 수는 없어, 쿼리별 부하를 재현하며 RSS 변화를 확인했다.

### 로컬에서 재현하기

운영과 같은 애플리케이션 빌드를 로컬 DB에 연결해 부하를 줬다. 프론트엔드에서 실제로 보내는 GraphQL 문서를 사용하고, 1초마다 `process.memoryUsage()`를 기록했다. 표의 차감값은 앞서 설명한 보조 지표이며, Prisma 엔진의 메모리를 직접 측정한 값은 아니다.

| 구간                                 | RSS             | 힙        | 차감값 변화 (추정) |
| ------------------------------------ | --------------- | --------- | ------------------ |
| 기술 상세 919건                      | 127 → 155MB     | +22MB     | +5MB               |
| 기술별 습득 포켓몬 919건 (캐시 미스) | 155 → **302MB** | +20MB     | **+128MB**         |
| 같은 쿼리 반복 (캐시 적중)           | 변화 없음       | 변화 없음 | 변화 없음          |

기술별 습득 포켓몬 목록을 캐시 없이 조회하는 구간에서 RSS는 155MB에서 302MB로 증가했고, 차감값도 128MB 늘었다. 같은 쿼리를 캐시 적중 상태로 반복했을 때는 이런 증가가 관측되지 않았다. 최종 응답은 평균 4.6KB였으므로, 응답을 만들기 위해 DB에서 더 많은 데이터를 조회하는지 확인했다.

## 7. 원인은 Prisma distinct였다

### distinct는 SQL DISTINCT가 아니었다

해당 서비스 코드를 따라가 보니 `distinct`를 쓰는 쿼리가 세 개 있었다. 그중 하나는 이렇게 생겼다.

```ts
// 폼에 자체 러닝셋 행이 하나라도 있는지 확인
const formsWithAnyRow = await prisma.pokemonLearnset.findMany({
  where: { formCode: { in: candidateCodes } },
  select: { formCode: true },
  distinct: ['formCode'],
});
```

코드만 보면 "폼 코드를 중복 없이 가져온다"로 읽힌다. SQL의 `SELECT DISTINCT`가 실행될 것으로 예상했지만, Prisma 5.7.0 릴리스 노트의 설명은 달랐다.

> Prisma Client handled the post-processing to select distinct records in-memory.

이 프로젝트는 Prisma 5.21.1을 사용했고, 미리보기 기능인 `nativeDistinct`는 비활성화돼 있었다. 이 구성에서 해당 `findMany` 쿼리는 **조건에 맞는 행을 가져온 뒤 쿼리 엔진 메모리에서 중복을 제거**했다. Prisma 5.7.0에서 도입된 `nativeDistinct`는 지원되는 PostgreSQL 쿼리에 SQL `DISTINCT ON`을 사용하는 기능이다. [Prisma 5.7.0 Release Notes](https://github.com/prisma/prisma/releases/tag/5.7.0)

### 쿼리 세 개가 가져온 440만 행

실제로 몇 행을 가져오는지 세어 봤다. `findMany`를 감싸서 `distinct` 인자가 있으면 같은 조건으로 `count()`를 함께 실행하고, 기술 919개를 캐시 없이 한 번씩 조회했다.

| 쿼리의 목적                         | 필요한 결과            | DB에서 가져온 행           | 실제로 쓴 행 |
| ----------------------------------- | ---------------------- | -------------------------- | ------------ |
| 기술의 습득 데이터가 있는 버전 목록 | 버전 ID 평균 11개      | 66만 (1회 최대 1.3만)      | 1만          |
| 폼이 그 버전에서 가진 습득법        | (폼, 습득법) 평균 39쌍 | 55만 (1회 최대 1.5만)      | 2.2만        |
| 폼에 자체 행이 하나라도 있는가      | 폼마다 있음/없음       | **318만 (1회 최대 8.2만)** | 1.1만        |

세 쿼리를 합쳐 **약 440만 행을 가져와 4.3만 행만 썼다.** 99%를 버리고 있었던 셈이다.

쿼리마다 사정도 조금씩 달랐다.

- 앞의 두 쿼리는 "서로 다른 값 목록"이 필요하니 `distinct`를 쓴 의도는 맞았다. Prisma가 그걸 메모리에서 처리한다는 게 문제였다.
- 세 번째 쿼리는 "행이 있는가"만 알면 되는 존재 확인이었다. 여기에 `distinct`를 쓰다 보니, 후보 폼이 배우는 모든 기술·모든 버전의 행을 전부 가져오고 있었다.
- 두 번째와 세 번째 쿼리의 결과는 **기술과 상관이 없었다.** 폼과 버전에만 달려 있는 값인데, 기술을 조회할 때마다 다시 계산하고 있었다.

### DB도 매번 테이블 전체를 읽고 있었다

DB의 실행 계획도 확인했다. 러닝셋 테이블(약 66만 행)에는 `form_code`로 시작하는 인덱스가 없었다. 로컬에서 확인한 세 번째 쿼리의 실행 계획은 테이블 전체를 읽는 병렬 순차 스캔이었다. [PostgreSQL — EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html)

| 실행 계획 (후보 폼 20개, 로컬) | 방식           | 돌려준 행 | 읽은 페이지            |
| ------------------------------ | -------------- | --------- | ---------------------- |
| 현재 쿼리                      | 병렬 순차 스캔 | 5,110     | 약 6,475 (테이블 전체) |
| `GROUP BY form_code`로 바꾸면  | 병렬 순차 스캔 | 20        | 약 6,491 (그대로)      |

`GROUP BY`로 바꾸면 돌려주는 행은 20개로 줄지만, 읽는 양은 그대로였다. 쿼리 모양을 바꾸는 것만으로는 부족하고, 같은 결과를 다시 계산하지 않는 방법이 필요하다는 뜻이었다. 이 내용은 2편의 수정 방향으로 이어진다.

## 8. 왜 하필 11월 4일부터였을까

### 재시작은 9월부터 있었다

원인을 찾고 나니, 그럼 왜 하필 11월 4일부터 심해졌는지가 궁금했다. `pm2.log`를 날짜별로 세어 보니 재시작은 새로운 일이 아니었다.

| 기간        | 하루 재시작  | 그 무렵 있었던 일                  |
| ----------- | ------------ | ---------------------------------- |
| 9/1~10/18   | 대부분 3~9회 | -                                  |
| 10/19~10/30 | 0~5회        | 10/19 쿼리 캐시에 바이트 상한 적용 |
| 10/31~11/3  | **0회**      | 10/30 러닝셋 조회 리팩터링 배포    |
| 11/4~11/11  | **5~16회**   | 11/3 프론트 prefetch 변경 배포     |

300MB 한도와 기본 메모리 사이의 여유가 원래 크지 않았다. 재시작 직후에도 RSS가 170~220MB였으니, 여유는 100MB 정도뿐이었다.

### 처음에는 코드 변경을 의심했다

10월 30일에 배포한 러닝셋 조회 리팩터링에서 세 번째 쿼리(폼에 행이 있는가)가 새로 생겼고, 두 번째 쿼리에서는 습득법 조건이 빠졌다. 캐시 미스 한 번의 비용이 커진 변경이라, 처음에는 이게 직접적인 원인이라고 봤다.

운영 배포 기록에서는 변경 후 **4일 동안 재시작이 관측되지 않았다.** 조회 비용이 커진 변경은 맞았지만, 재시작 증가 시점을 설명하려면 당시 요청량과 요청 구성도 함께 봐야 했다.

### 두 변화가 겹친 시점

재시작이 다시 증가한 시점은 프론트엔드 prefetch 변경을 배포한 다음 날이었다. API 요청도 하루 약 39만 건에서 60만 건 이상으로 늘었다. 배포 기록과 로컬 재현 결과를 종합하면 다음과 같은 경로를 추정할 수 있었다.

```text
10/30  러닝셋 리팩터링  → 캐시 미스 1회의 비용이 커짐
11/3   prefetch 변경    → API 요청 증가와 시점이 겹침
       + 봇 크롤링      → 서로 다른 기술·버전 조합 요청
                ↓
캐시 미스 → 대량 행 조회 → RSS 증가 → PM2 재시작 기준 초과
→ PM2 재시작 → 쿼리 캐시가 비워짐 → 캐시 미스 증가 → (반복)
```

프로세스가 재시작되면 캐시가 비워지므로, 같은 요청도 다시 DB 조회를 수행한다. 이 구조는 재시작 후 메모리 사용량이 다시 증가하는 현상을 설명할 수 있었다. DB 컨테이너 송신량도 8월 말 시작 이후 일평균 약 12GB에 비해 수정 직전 하루에는 약 35GB로 많았다. 다만 두 값의 집계 기간이 달라, 변경 효과를 직접 비교하는 지표로 사용하지는 않았다.

## 9. 조사하면서 틀렸던 것들

원인을 찾기까지 몇 번 잘못 짚었다. 다음에 비슷한 문제를 볼 때 참고하려고 남겨 둔다.

### 서버 전체 그래프로 프로세스를 판단했다

graceful shutdown을 고친 다음 날, CloudWatch의 서버 전체 메모리 그래프를 보고 "재시작 흔적이 없다"고 판단했다. 5분 평균 그래프에서 메모리가 갑자기 떨어지는 구간이 없었기 때문이다.

실제로는 그날 하루에만 10번 재시작되고 있었다. API 프로세스 하나가 재시작될 때 줄어드는 메모리는 서버 전체의 7~8% 정도라, 5분 평균에 묻혀 보이지 않았다. 프로세스의 상태는 프로세스의 기록(`pm2.log`, 계측 로그)으로 확인해야 했다.

### 측정 스크립트도 틀릴 수 있다

수정 전후의 행 수를 다시 셀 때, 같은 조건인데 전날 440만 행이던 값이 209만 행으로 나왔다. 데이터가 바뀌었는지 의심했는데, 원인은 측정 스크립트였다.

```ts
// 틀린 코드: await를 기다리기 전에 fetched의 현재 값을 먼저 읽는다
stats.fetched += await prisma.pokemonLearnset.count({ where });

// 맞는 코드
const fetched = await prisma.pokemonLearnset.count({ where });
stats.fetched += fetched;
```

`a += await b`는 `a`의 현재 값을 먼저 읽어 둔 뒤 `b`를 기다린다. 두 작업이 같은 누적값을 공유하고 `await` 구간이 겹치면, 각자 읽어 둔 값에 결과를 더해 쓰면서 다른 작업의 갱신을 덮어쓸 수 있다. 전날 사용한 스크립트로 같은 빌드를 다시 실행해 약 440만 행이 조회되는 것을 확인했다.

## 마치며

처음에는 비용이 줄었는지만 보려고 했다. 그런데 비용 지표 옆의 요청 수와 응답 시간, 메모리를 같이 보면서 API 서버의 재시작을 발견할 수 있었다. 원인을 좁혀 가는 동안에는 가설을 세우고, 계측 로그나 로컬 재현처럼 직접 확인할 수 있는 근거로 하나씩 지워 나갔다.

주요 원인으로 확인한 것은 당시 Prisma 구성에서 `distinct`가 중복 제거를 쿼리 엔진 메모리에서 수행한다는 점이었다. 최종 결과에 비해 많은 행을 조회했고, 해당 쿼리의 캐시 미스 구간에서 RSS 증가를 재현했다. ORM 코드를 읽는 것과 함께 실제 SQL과 실행 계획을 확인해야 하는 이유였다.

다음 편에서는 재시작 중 요청 실패를 줄이고, 봇을 차단하고, `distinct`를 `groupBy`와 메모이제이션으로 바꾼 과정을 다룬다. 배포 후 운영 지표로 효과를 확인한 결과도 함께 정리한다.
