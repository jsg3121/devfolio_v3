## 들어가며

> 이 글은 **포케코리아 API 서버 메모리 장애 추적기** 시리즈의 첫 번째 글입니다.
>
> 1편 원인 파악 → 2편 대응과 검증

11월 초에 포케코리아의 CloudFront 비용을 줄이는 작업을 했다. Next.js `<Link>`가 화면에 보이기만 한 링크까지 미리 받아 오는(prefetch) 바람에 요청 수가 크게 늘어 있었고, 이걸 사용자가 누르려 할 때만 받아 오도록 바꿨다. 일주일쯤 지나 실제로 비용이 줄었는지 확인하러 들어갔다.

비용은 줄고 있었다. 그런데 그 옆의 지표들이 이상했다. 웹 서버로 가는 요청은 절반이 됐는데 API 서버로 가는 요청은 오히려 늘어 있었고, 서버 메모리는 조금씩 오르고 있었다. 확인해 보니 API 서버가 메모리 한도에 걸려 **하루 10~16번씩 재시작**되고 있었다.

이번 글에서는 이 재시작의 원인을 찾아가는 과정을 정리해 보려고 한다. 잘못 짚은 가설도 몇 개 있었는데, 그것도 함께 적었다. 원인을 고치고 효과를 확인한 과정은 2편에서 이어서 다룬다.

시각은 모두 한국 시간 기준이다. 코드는 설명에 필요 없는 부분을 덜어 냈다.

## 1. 운영 환경

[지난 장애](/articles/poke-korea-cpu-credit-exhaustion) 이후 인스턴스를 t3.small로 바꿨고, 구성은 그대로다. 서버 한 대에 모든 프로세스가 올라가 있다.

```
CloudFront (웹, 이미지)
  │
  ▼
ALB
  ├─ 웹       → :80    Next.js (App Router)
  ├─ API      → :4000  Apollo Server + Prisma
  └─ 블로그   → :3001  Docusaurus
  │
  ▼
EC2 t3.small (2 vCPU / 2GB)
  ├─ PM2로 웹·API·블로그 프로세스 실행
  └─ Docker PostgreSQL
```

지난 장애와 비교하면 두 가지가 달라졌다.

- **API 도메인이 CloudFront를 거치지 않는다.** 비용 절감 작업 중 11월 2일에 API 도메인을 ALB로 바로 연결했다. API 응답은 캐시하지 않아서 CloudFront를 거칠 이유가 없었다.
- **API 서버에 graceful shutdown이 있다.** 지난 장애 때 추가했다. 종료 신호를 받으면 `server.close()`로 연결을 정리하고, 4초 안에 끝나지 않으면 강제 종료한다.

## 2. 비용은 정말 줄고 있었을까

### 하루 금액만 보면 착시가 생긴다

Cost Explorer에서 CloudFront의 일별 금액을 보면 효과가 아주 커 보였다. 10월 말에는 하루 1.2달러 정도였는데, 11월 들어서는 0.05달러 정도로 떨어져 있었다.

그런데 10월 초의 금액을 같이 보니 이상한 점이 있었다.

| 기간        | 하루 금액     |
| ----------- | ------------- |
| 10/1~10/18  | 0.16~0.22달러 |
| 10/19~10/31 | 1.08~1.43달러 |
| 11/1 이후   | 0.05~0.08달러 |

같은 10월인데 19일을 기준으로 금액이 6배가 됐다. 이유는 CloudFront의 월 무료 한도였다. CloudFront는 매달 요청 1,000만 건까지 무료이고, 이 서비스의 비용은 거의 전부 요청 수 과금이었다. 10월에는 19일에 무료 한도를 다 쓰면서 금액이 뛰었고, 11월 1일에 한도가 다시 채워지면서 금액이 떨어진 것이었다. [Amazon CloudFront — 요금](https://aws.amazon.com/cloudfront/pricing/)

그러니 11월의 낮은 금액은 내가 한 작업의 효과가 아니라 무료 한도 덕분이었다. 효과를 보려면 금액이 아니라 **요청 수**를 비교해야 했다.

### 요청 수로 다시 보기

CloudWatch의 CloudFront `Requests` 지표로 하루 평균을 비교했다.

| 배포          | 10/20~10/31 | 11/4~11/9     | 변화     |
| ------------- | ----------- | ------------- | -------- |
| 웹            | 44.4만      | 25.4만        | −43%     |
| API           | 약 40만     | 0             | −100%    |
| 이미지        | 11.8만      | 12.6만        | +7%      |
| **계정 전체** | **약 99만** | **약 38.5만** | **−61%** |

이미지 요청은 7% 늘었으니 사용자가 줄어서 요청이 줄어든 건 아니었다. 비용 절감은 실제로 되고 있었다. 여기까지는 예상대로였다.

## 3. 웹은 줄었는데 API는 늘었다

이상한 건 CloudFront 뒤쪽이었다. ALB 지표를 대상 그룹별로 나눠 보니 웹과 API가 반대로 움직이고 있었다.

| ALB 대상 그룹 (하루)   | 10/25~11/1 | 11/4~11/9 |
| ---------------------- | ---------- | --------- |
| 웹 요청                | 약 26만    | 약 12.8만 |
| API 요청               | 약 39만    | 60만~81만 |
| 웹 요청 1건당 API 호출 | 1.6        | 5.2       |
| 웹 평균 응답시간       | 22~38ms    | 74~114ms  |
| API 평균 응답시간      | 20~24ms    | 43~60ms   |

웹 서버의 요청이 절반이 됐는데 API 서버의 요청은 1.5~2배가 됐다. 응답 시간은 둘 다 2~3배 느려졌다. 같은 기간 서버 메모리 평균도 47%에서 68%까지 매일 조금씩 오르고 있었다.

API 도메인을 ALB로 바로 연결한 것 때문인지 먼저 의심했다. 하지만 기존 API용 CloudFront 배포는 캐시가 꺼져 있었고(`Managed-CachingDisabled`), WAF나 응답 헤더 정책도 없었다. 예전에도 API 요청은 전부 ALB까지 왔다는 뜻이라, 연결 방식이 바뀐 것만으로는 요청이 늘 이유가 없었다.

## 4. 액세스 로그로 범위 좁히기

CloudFront 액세스 로그는 S3에 쌓이고 있어서, 작업 전후의 같은 요일(10월 28일, 11월 4일)을 하루씩 받아 비교했다.

### 웹 요청 하나가 API를 몇 번 부를까

웹 서버까지 온 요청(CloudFront 캐시 미스)을 RSC 요청과 문서 요청으로 나누고, 시간대별로 ALB의 API 요청 수와 맞춰 봤다. 시간대마다 "API 요청 수 = RSC × a + 문서 × b" 꼴로 회귀를 돌리면, 요청 하나가 API를 몇 번 부르는지 대략 알 수 있다.

| 웹 서버까지 온 요청 1건당 API 호출 | 10/28    | 11/4     |
| ---------------------------------- | -------- | -------- |
| RSC 요청                           | 약 0회   | 약 2회   |
| 문서 요청                          | 약 7.7회 | 약 7.8회 |

24개 시간대로 낸 추정이라 숫자 자체는 대략적인 값이다. 그래도 방향은 분명했다.

RSC 요청 1건이 부르는 API가 0회에서 2회가 된 건 prefetch 방식을 바꾼 영향이었다. 화면에 보인 링크를 미리 받던 예전 방식은 로딩 경계까지만 받아서 API를 거의 부르지 않았다. 바꾼 방식은 사용자가 누르려 할 때 `router.prefetch()`로 받는데, 이 프로젝트의 Next.js 15 설정에서 이 함수의 기본값은 `FULL`이다. 실제로 이동할 때와 똑같이 페이지 전체를 렌더링한다는 뜻이다. 요청 수는 줄었지만 요청 하나가 무거워진 셈이다.

### 웹 서버까지 오는 문서 요청의 80%가 봇이었다

API 호출의 대부분은 문서 요청에서 나오고 있었다. 그래서 문서 요청을 User-Agent별로 나눠 봤다.

| UA (11/4)         | 웹 서버까지 온 문서 요청 | 검색·광고 관련성          |
| ----------------- | ------------------------ | ------------------------- |
| `meta-webindexer` | 7,154                    | Meta AI 검색              |
| `QlyzeBot`        | 6,668                    | 없음                      |
| `SemrushBot`      | 4,638                    | 없음 (SEO 분석 도구)      |
| `Baiduspider`     | 3,175                    | 한국어 서비스라 거의 없음 |
| `ExaSearchBot`    | 2,083                    | 낮음                      |

캐시를 통과해 웹 서버까지 온 문서 요청의 약 80%가 봇이었다. 특히 `QlyzeBot`은 IP 하나로 한 시간 동안 6,668페이지를 요청했고, 그 시간대 API 요청이 평소의 3배 가까이 튀었다.

### 모든 페이지가 매번 새로 그려지고 있었다

문서 요청 하나가 API를 8번 가까이 부른다는 것도 이상했다. 상세 페이지 대부분은 `revalidate = 31536000`으로 ISR을 설정해 두었기 때문에, 처음 한 번만 렌더링하고 이후에는 캐시에서 응답해야 했다.

그런데 빌드 결과의 `prerender-manifest.json`을 열어 보니 ISR로 잡힌 경로가 하나도 없었다. 정적으로 만들어진 건 `robots.txt`, `sitemap.xml`, `manifest.webmanifest` 세 개뿐이었다.

```tsx
// app/layout.tsx
export default async function RootLayout({ children }: RootLayoutProps) {
  const headersList = await headers();
  const userAgent = headersList.get('user-agent') || '';
  const isMobile = detectUserAgent(userAgent);
  // ...
}
```

루트 레이아웃이 기기를 판별하려고 `headers()`를 쓰고 있었다. `headers()`는 요청마다 값이 달라지는 동적 API라서, 레이아웃에서 쓰면 그 아래 모든 경로가 동적 렌더링으로 바뀐다. [Next.js — headers](https://nextjs.org/docs/app/api-reference/functions/headers) 그동안 `revalidate`는 아무 효과가 없었고, CloudFront 캐시를 통과한 요청은 사람이든 봇이든 매번 SSR을 다시 실행하고 있었다.

여기까지 정리하면 이렇다. 봇과 prefetch가 웹 서버까지 오는 요청을 만들고, 그 요청은 매번 페이지 전체를 렌더링하면서 API를 여러 번 부르고 있었다.

## 5. API 서버는 왜 재시작되고 있었나

API 요청이 늘어난 이유는 어느 정도 보였다. 그런데 요청이 늘었다고 서버가 재시작되는 건 별개의 문제다. 서버에 들어가 프로세스 상태를 확인했다.

### 크래시가 아니라 메모리 한도였다

`pm2 list`에서 API 프로세스의 재시작 횟수는 79였고, 가동 시간은 28분이었다. 크래시 반복(`unstable restarts`)은 0이었고 `dmesg`에도 OOM 흔적이 없었다. 원인은 `pm2.log`에 그대로 남아 있었다.

```
PM2 log: [PM2][WORKER] Process 5 restarted because it exceeds --max-memory-restart value
  (current_memory=316215296 max_memory_limit=314572800 [octets])
```

PM2의 `max_memory_restart`를 300MB로 설정해 두었는데, 메모리가 이 값을 넘을 때마다 PM2가 프로세스를 다시 띄우고 있었다. [PM2 — Max Memory Threshold Auto Reload](https://pm2.keymetrics.io/docs/usage/memory-limit/) 하루 동안의 재시작 간격을 보면 짧게는 9분이었다.

### 재시작할 때마다 요청이 실패하고 있었다

재시작 자체보다 더 아팠던 건 재시작하는 동안의 실패였다. API 서버의 에러 로그에는 같은 메시지가 수천 줄 쌓여 있었다.

```
A GraphQL operation was received during server shutdown. The operation will fail.
Consider draining the HTTP server on shutdown
정리 시간 초과. 강제 종료
```

ALB 지표로 봐도 API 5xx는 11월 3일까지 하루 0~6건이었다가 11월 4일부터 하루 67~447건이 됐다. ELB 502도 하루 13~107건에서 94~453건으로 늘었다.

graceful shutdown을 넣어 뒀는데 왜 종료 중에 요청이 실패할까. Apollo Server 문서를 다시 읽고 나서야 이유를 알 수 있었다. Apollo Server는 `stopOnTerminationSignals` 옵션이 기본으로 켜져 있어서, `SIGINT`를 받으면 **스스로 먼저 멈춘다.** [Apollo Server — stopOnTerminationSignals](https://www.apollographql.com/docs/apollo-server/api/apollo-server#stoponterminationsignals)

```text
SIGINT 수신
  ├─ Apollo: 바로 stop()  →  이후 들어오는 GraphQL 요청은 전부 실패
  └─ 내 핸들러: server.close()  →  새 연결만 막음
        └─ ALB가 열어 둔 keep-alive 연결로는 요청이 계속 들어옴
           → 연결이 비지 않아 close()가 끝나지 않음
           → 4초 뒤 강제 종료 (exit 1)
```

`server.close()`는 새 연결을 막을 뿐이고, 이미 열려 있는 keep-alive 연결로는 요청이 계속 들어온다. 그 요청들을 이미 멈춘 Apollo가 받으면서 500이 쏟아졌다. 지난 장애 때 넣은 graceful shutdown은 소켓을 정리하는 데는 도움이 됐지만, Apollo가 먼저 멈추는 문제까지는 막지 못하고 있었다.

이 부분은 원인이 분명해서 먼저 고쳤다. 고친 방법은 2편에서 다룬다. 다만 이건 재시작할 때의 피해를 줄이는 일이고, 재시작 자체는 그대로였다. 메모리가 왜 300MB를 넘는지를 찾아야 했다.

## 6. 메모리는 어디서 늘어나고 있었나

### 처음에는 캐시를 의심했다

API 서버에는 쿼리 결과를 담는 LRU 캐시가 있다. 상한은 64MB인데, 이 크기를 `JSON.stringify` 결과의 바이트 수로 계산하고 있었다. 캐시에 실제로 들어 있는 건 문자열이 아니라 JS 객체이고, 같은 데이터라도 객체는 힙에서 JSON 문자열보다 크게 잡힐 수 있다. 그렇다면 "64MB 상한"이 실제로는 200~300MB가 될 수도 있겠다고 생각했다.

추측만으로 상한을 바꾸기는 싫어서, 1분마다 메모리와 캐시 크기를 남기는 계측 로그를 먼저 추가했다.

```ts
const reportMemory = () => {
  const { rss, heapTotal, heapUsed, external } = process.memoryUsage();
  const cache = getQueryCacheStats();

  console.log(
    `[memory] ${JSON.stringify({
      at: new Date().toISOString(),
      rssMB: toMB(rss),
      heapTotalMB: toMB(heapTotal),
      heapUsedMB: toMB(heapUsed),
      externalMB: toMB(external),
      cacheMB: cache.usedMB,
      cacheEntries: cache.size,
    })}`,
  );
};
```

하루치 로그를 받아 보니 예상과 전혀 달랐다.

| 값                       | 범위                                 |
| ------------------------ | ------------------------------------ |
| `heapUsed` / `heapTotal` | 27~88MB / 47~108MB                   |
| 캐시 크기                | 1.8~18MB (항목 수는 거의 항상 2,000) |
| `rss`                    | 169~283MB, 재시작 직전 315~385MB     |

캐시는 64MB 상한에 한참 못 미쳤다. 항목 수가 늘 2,000개 상한에 걸려 있었을 뿐이다. JS 힙도 100MB 안팎에서 안정적이었다. 캐시 가설은 여기서 접었다.

### 힙 밖에서 늘어나는 메모리

남는 건 `rss − heapTotal − external`, 즉 JS 힙 밖의 메모리였다. 이 값이 120~200MB로 RSS의 대부분을 차지하고 있었다. [Node.js — process.memoryUsage()](https://nodejs.org/api/process.html#processmemoryusage)

Node 프로세스 안에서 힙 밖의 메모리를 크게 쓸 만한 건 Prisma였다. Prisma 5의 쿼리 엔진은 Rust로 만든 네이티브 라이브러리(`libquery_engine*.node`)로, Node 프로세스 안에서 돈다. DB에서 받은 행은 이 엔진의 메모리에서 먼저 처리되기 때문에, 엔진이 쓰는 메모리는 JS 힙이 아니라 RSS에만 잡힌다.

### 로컬에서 재현하기

어느 쿼리가 네이티브 메모리를 키우는지 보려고, 운영과 같은 빌드를 로컬 DB에 연결해 부하를 줬다. 프론트가 실제로 보내는 GraphQL 문서를 그대로 쓰고, 1초마다 `process.memoryUsage()`를 기록했다.

| 구간                                 | RSS             | 힙        | 네이티브   |
| ------------------------------------ | --------------- | --------- | ---------- |
| 기술 상세 919건                      | 127 → 155MB     | +22MB     | +5MB       |
| 기술별 습득 포켓몬 919건 (캐시 미스) | 155 → **302MB** | +20MB     | **+128MB** |
| 같은 쿼리 반복 (캐시 적중)           | 변화 없음       | 변화 없음 | 변화 없음  |

기술별 습득 포켓몬 목록을 캐시 없이 조회하는 구간에서만 네이티브 메모리가 128MB 늘었고, RSS는 운영 한도인 300MB를 넘었다. 그런데 이 쿼리의 응답은 평균 4.6KB밖에 되지 않았다. 응답은 작은데 메모리는 크게 늘어난다면, DB에서 응답보다 훨씬 많은 데이터를 가져오고 있을 가능성이 컸다.

## 7. 원인은 Prisma distinct였다

### distinct는 SQL DISTINCT가 아니었다

해당 서비스 코드를 따라가 보니 `distinct`를 쓰는 쿼리가 세 개 있었다. 그중 하나는 이렇게 생겼다.

```ts
// 폼에 자체 러닝셋 행이 하나라도 있는지 확인
const formsWithAnyRow = await prisma.pokemonLearnset.findMany({
  where: { formCode: { in: candidateCodes } },
  select: { formCode: true },
  distinct: ['formCode'],
});
```

코드만 보면 "폼 코드를 중복 없이 가져온다"로 읽힌다. SQL의 `SELECT DISTINCT`가 나갈 거라고 생각하기 쉽다. 그런데 Prisma 5.7.0 릴리즈 노트에는 이렇게 적혀 있다.

> Prisma Client handled the post-processing to select distinct records in-memory.

Prisma의 `distinct`는 조건에 맞는 행을 **전부 가져온 뒤 엔진 메모리에서 중복을 거른다.** PostgreSQL에서 SQL `DISTINCT ON`을 쓰려면 미리보기 기능인 `nativeDistinct`를 따로 켜야 한다. [Prisma 5.7.0 Release Notes](https://github.com/prisma/prisma/releases/tag/5.7.0) 이 프로젝트는 Prisma 5.21.1이었고, `nativeDistinct`는 켜지 않은 상태였다.

### 쿼리 세 개가 가져온 440만 행

실제로 몇 행을 가져오는지 세어 봤다. `findMany`를 감싸서 `distinct` 인자가 있으면 같은 조건으로 `count()`를 함께 실행하고, 기술 919개를 캐시 없이 한 번씩 조회했다.

| 쿼리의 목적                         | 필요한 결과            | DB에서 가져온 행           | 실제로 쓴 행 |
| ----------------------------------- | ---------------------- | -------------------------- | ------------ |
| 기술의 습득 데이터가 있는 버전 목록 | 버전 ID 평균 11개      | 66만 (1회 최대 1.3만)      | 1만          |
| 폼이 그 버전에서 가진 습득법        | (폼, 습득법) 평균 39쌍 | 55만 (1회 최대 1.5만)      | 2.2만        |
| 폼에 자체 행이 하나라도 있는가      | 폼마다 있음/없음       | **318만 (1회 최대 8.2만)** | 1.1만        |

세 쿼리를 합쳐 **약 440만 행을 가져와 4.3만 행만 썼다.** 99%를 버리고 있었던 셈이다.

쿼리마다 사정도 조금씩 달랐다.

- 앞의 두 쿼리는 "서로 다른 값 목록"이 필요하니 `distinct`를 쓴 의도는 맞았다. Prisma가 그걸 메모리에서 처리한다는 게 문제였다.
- 세 번째 쿼리는 "행이 있는가"만 알면 되는 존재 확인이었다. 여기에 `distinct`를 쓰다 보니, 후보 폼이 배우는 모든 기술·모든 버전의 행을 전부 가져오고 있었다.
- 두 번째와 세 번째 쿼리의 결과는 **기술과 상관이 없었다.** 폼과 버전에만 달려 있는 값인데, 기술을 조회할 때마다 다시 계산하고 있었다.

### DB도 매번 테이블 전체를 읽고 있었다

Node 쪽만의 문제도 아니었다. 러닝셋 테이블(약 66만 행)에는 `form_code`로 시작하는 인덱스가 없어서, 세 번째 쿼리는 실행할 때마다 테이블 전체를 읽고 있었다. [PostgreSQL — EXPLAIN](https://www.postgresql.org/docs/current/sql-explain.html)

| 실행 계획 (후보 폼 20개, 로컬) | 방식           | 돌려준 행 | 읽은 페이지            |
| ------------------------------ | -------------- | --------- | ---------------------- |
| 현재 쿼리                      | 병렬 순차 스캔 | 5,110     | 약 6,475 (테이블 전체) |
| `GROUP BY form_code`로 바꾸면  | 병렬 순차 스캔 | 20        | 약 6,491 (그대로)      |

`GROUP BY`로 바꾸면 돌려주는 행은 20개로 줄지만, 읽는 양은 그대로였다. 쿼리 모양을 바꾸는 것만으로는 부족하고, 같은 결과를 다시 계산하지 않는 방법이 필요하다는 뜻이었다. 이 내용은 2편의 수정 방향으로 이어진다.

## 8. 왜 하필 11월 4일부터였을까

### 재시작은 9월부터 있었다

원인을 찾고 나니, 그럼 왜 하필 11월 4일부터 심해졌는지가 궁금했다. `pm2.log`를 날짜별로 세어 보니 재시작은 새로운 일이 아니었다.

| 기간        | 하루 재시작  | 그 무렵 있었던 일                  |
| ----------- | ------------ | ---------------------------------- |
| 9/1~10/18   | 대부분 3~9회 | -                                  |
| 10/19~10/30 | 0~5회        | 10/19 쿼리 캐시에 바이트 상한 적용 |
| 10/31~11/3  | **0회**      | 10/30 러닝셋 조회 리팩터링 배포    |
| 11/4~11/11  | **5~16회**   | 11/3 프론트 prefetch 변경 배포     |

300MB 한도와 기본 메모리 사이의 여유가 원래 크지 않았다. 재시작 직후에도 RSS가 170~220MB였으니, 여유는 100MB 정도뿐이었다.

### 처음에는 코드 변경을 의심했다

10월 30일에 배포한 러닝셋 조회 리팩터링에서 세 번째 쿼리(폼에 행이 있는가)가 새로 생겼고, 두 번째 쿼리에서는 습득법 조건이 빠졌다. 캐시 미스 한 번의 비용이 커진 변경이라, 처음에는 이게 직접적인 원인이라고 봤다.

그런데 운영 서버의 배포 기록을 확인해 보니, 이 변경이 들어간 뒤 **4일 동안 재시작이 한 번도 없었다.** 이 변경만으로는 재시작이 일어나지 않았다는 뜻이다.

### 두 변화가 겹친 시점

재시작이 다시 시작된 건 프론트 prefetch 변경을 배포한 다음 날부터였다. 그날부터 API 요청이 하루 39만 건에서 60만 건 이상으로 늘었다. 정리하면 이런 구조였다.

```text
10/30  러닝셋 리팩터링  → 캐시 미스 1회의 비용이 커짐
11/3   prefetch 변경    → 미스를 만드는 요청이 늘어남
       + 봇 크롤링      → 서로 다른 기술·버전 조합 요청
                ↓
캐시 미스 → 대량 행 조회 → 네이티브 메모리 증가 → 300MB 초과
→ PM2 재시작 → 쿼리 캐시가 비워짐 → 캐시 미스 증가 → (반복)
```

재시작이 캐시를 비우고, 비워진 캐시가 다시 미스를 늘리면서 스스로를 키우는 순환이 생기고 있었다. DB 컨테이너가 보낸 데이터는 컨테이너가 시작된 8월 말 이후 평균 하루 약 12GB였는데, 수정 직전 하루는 약 35GB였다.

## 9. 조사하면서 틀렸던 것들

원인을 찾기까지 몇 번 잘못 짚었다. 다음에 비슷한 문제를 볼 때 참고하려고 남겨 둔다.

### 서버 전체 그래프로 프로세스를 판단했다

graceful shutdown을 고친 다음 날, CloudWatch의 서버 전체 메모리 그래프를 보고 "재시작 흔적이 없다"고 판단했다. 5분 평균 그래프에서 메모리가 갑자기 떨어지는 구간이 없었기 때문이다.

실제로는 그날 하루에만 10번 재시작되고 있었다. API 프로세스 하나가 재시작될 때 줄어드는 메모리는 서버 전체의 7~8% 정도라, 5분 평균에 묻혀 보이지 않았다. 프로세스의 상태는 프로세스의 기록(`pm2.log`, 계측 로그)으로 확인해야 했다.

### 측정 스크립트도 틀릴 수 있다

수정 전후의 행 수를 다시 셀 때, 같은 조건인데 전날 440만 행이던 값이 209만 행으로 나왔다. 데이터가 바뀌었는지 의심했는데, 원인은 측정 스크립트였다.

```ts
// 틀린 코드: await를 기다리기 전에 fetched의 현재 값을 먼저 읽는다
stats.fetched += await prisma.pokemonLearnset.count({ where });

// 맞는 코드
const fetched = await prisma.pokemonLearnset.count({ where });
stats.fetched += fetched;
```

`a += await b`는 `a`의 현재 값을 먼저 읽어 둔 뒤 `b`를 기다린다. 두 쿼리가 `Promise.all`로 동시에 실행되면 둘 다 같은 옛 값을 읽어 두었다가 각자 더해 쓰기 때문에, 한쪽 결과가 사라진다. 전날 쓴 스크립트로 같은 빌드를 다시 돌려 440만 행이 그대로 나오는 걸 확인하고서야 안심할 수 있었다.

## 마치며

처음에는 비용이 줄었는지만 보려고 했다. 그런데 비용 지표 옆의 요청 수와 응답 시간, 메모리를 같이 보면서 API 서버의 재시작을 발견할 수 있었다. 원인을 좁혀 가는 동안에는 가설을 세우고, 계측 로그나 로컬 재현처럼 직접 확인할 수 있는 근거로 하나씩 지워 나갔다.

결국 원인은 Prisma `distinct`가 SQL이 아니라 메모리에서 중복을 거른다는 점이었다. 코드만 보면 문제없어 보이는 쿼리가 필요한 양의 수백 배 행을 가져오고 있었다. ORM이 실제로 어떤 쿼리를 보내는지는 코드가 아니라 쿼리 로그나 실행 계획으로 확인해야 한다는 걸 다시 느꼈다.

다음 편에서는 재시작 중 요청 실패를 막고, 봇을 차단하고, `distinct`를 `groupBy`와 메모이제이션으로 바꾼 과정을 다룬다. 배포 후 6일 동안의 지표로 효과를 확인한 결과도 함께 정리한다.
