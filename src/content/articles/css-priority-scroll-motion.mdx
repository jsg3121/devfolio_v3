## 들어가며

GSAP ScrollTrigger로 구현한 커리어 타임라인에 다크모드를 적용하면서, 스크롤 시 타임라인 노드가 활성화되지 않는 버그가 발생했다. 원인은 Tailwind CSS 유틸리티 클래스와 커스텀 CSS 클래스 사이의 **우선순위(specificity) 충돌**이었다.

이 글에서는 CSS 우선순위가 어떻게 동작하는지, Tailwind v4에서 이런 충돌이 왜 발생하는지, 그리고 어떻게 해결했는지를 정리한다.

## 문제 상황

### 원래 동작 (다크모드 적용 전)

타임라인의 각 노드는 스크롤 위치에 따라 JavaScript로 클래스를 토글하여 활성 상태를 표현했다.

```javascript
// GSAP ScrollTrigger 콜백 내부
const activateNode = (node) => {
  node.classList.remove('border-gray-300', 'bg-white');
  node.classList.add('border-gray-900', 'bg-gray-900');
};
```

Tailwind 클래스를 직접 add/remove하는 방식이었고, 정상 동작했다.

### 다크모드 적용 후 (버그 발생)

다크모드 대응을 위해 초기 상태에 `dark:` variant를 추가하고, 활성 상태는 커스텀 CSS 클래스로 변경했다.

```html
<!-- 초기 상태: Tailwind 유틸리티 -->
<div class="timeline-node border-gray-300 dark:border-slate-600 bg-white dark:bg-slate-900">
</div>
```

```css
/* 활성 상태: 커스텀 CSS */
.timeline-node-active {
  border-color: #111827;
  background-color: #111827;
}
```

```javascript
// JavaScript에서 클래스 추가
node.classList.add('timeline-node-active');
```

결과: **노드가 활성화되지 않았다.** `.timeline-node-active`의 스타일이 적용되지 않는 것처럼 보였다.

## 원인 분석: CSS 우선순위

### CSS Specificity(명시도) 규칙

CSS에서 같은 요소에 여러 규칙이 적용될 때, 어떤 규칙이 우선하는지를 결정하는 기준이 specificity다.

```
인라인 스타일 (1,0,0,0)  >  ID (0,1,0,0)  >  클래스 (0,0,1,0)  >  태그 (0,0,0,1)
```

`.timeline-node-active`와 `.border-gray-300`은 둘 다 클래스 선택자로, specificity가 동일하다 `(0,0,1,0)`. 이 경우 **나중에 선언된 규칙이 우선**한다(cascade 순서).

### Tailwind v4의 레이어 구조

Tailwind CSS v4는 CSS의 `@layer` 기능을 활용한다.

```css
@layer theme, base, components, utilities;
```

유틸리티 클래스(`.border-gray-300`, `.bg-white` 등)는 `utilities` 레이어에 속한다. **`@layer` 바깥에 있는 CSS는 모든 레이어보다 우선**해야 하지만, Tailwind v4에서 유틸리티 레이어는 가장 마지막에 위치하여 높은 cascade 우선순위를 갖는다.

Astro 컴포넌트의 `<style>` 블록은 Tailwind의 레이어 구조와 별도로 생성된다. 하지만 빌드 과정에서 CSS가 병합될 때, Tailwind 유틸리티가 컴포넌트 스타일보다 **나중에** 위치하게 되면서 유틸리티 클래스가 커스텀 CSS를 덮어쓰는 상황이 발생했다.

```
빌드 결과 CSS 순서:
  1. 컴포넌트 <style> 블록 (.timeline-node-active)
  2. Tailwind 유틸리티 (.border-gray-300, .dark\:border-slate-600)
  ↑ 나중에 선언된 Tailwind이 우선
```

### 핵심: 같은 속성을 두 곳에서 선언

문제의 본질은 `border-color`와 `background-color`를 **Tailwind 유틸리티(초기 상태)**와 **커스텀 CSS(활성 상태)**에서 동시에 선언한 것이다.

```
요소에 적용된 클래스:
  border-gray-300         → border-color: #d1d5db  (Tailwind, utilities 레이어)
  dark:border-slate-600   → border-color: #475569  (Tailwind, utilities 레이어)
  timeline-node-active    → border-color: #111827  (커스텀, 레이어 없음)
```

JavaScript로 `timeline-node-active` 클래스를 추가해도, 기존 `border-gray-300` 클래스가 여전히 요소에 남아있었다. cascade 순서에서 Tailwind 유틸리티가 뒤에 위치하므로, 커스텀 CSS의 값은 무시되었다.

## 해결 방법

### 적용한 방법: 같은 관리 체계로 통일

초기 상태와 활성 상태를 **모두 커스텀 CSS로 통일**하여 cascade 충돌을 원천 차단했다.

```html
<!-- Tailwind 유틸리티 대신 커스텀 클래스만 사용 -->
<div class="timeline-node"></div>
```

```css
/* 초기 상태 */
.timeline-node {
  border-color: #d1d5db;
  background-color: #ffffff;
}

:global(.dark) .timeline-node {
  border-color: #475569;
  background-color: #0f172a;
}

/* 활성 상태 — 같은 파일, 후순위로 선언 */
.timeline-node-active {
  border-color: #111827 !important;
  background-color: #111827 !important;
}

:global(.dark) .timeline-node-active {
  border-color: #e2e8f0 !important;
  background-color: #e2e8f0 !important;
}
```

같은 `<style>` 블록 내에서 선언 순서로 우선순위를 보장하고, `!important`를 추가하여 확실하게 덮어쓰도록 했다.

### 대안: JavaScript에서 클래스를 완전히 교체

초기 방식처럼 JavaScript에서 Tailwind 클래스를 직접 remove/add하는 방법도 있다. 하지만 다크모드에서는 조건 분기가 필요해서 코드가 복잡해진다.

```javascript
// 다크모드 분기가 필요해져서 복잡도가 증가
const isDark = document.documentElement.classList.contains('dark');
node.classList.remove(
  'border-gray-300', 'bg-white',
  'dark:border-slate-600', 'dark:bg-slate-900'
);
node.classList.add(
  isDark ? 'border-slate-200' : 'border-gray-900',
  isDark ? 'bg-slate-200' : 'bg-gray-900'
);
```

CSS로 통일하면 JavaScript는 클래스 하나만 토글하면 되므로 훨씬 깔끔하다.

## GSAP과 CSS 우선순위

GSAP은 인라인 스타일(`element.style`)로 애니메이션을 적용한다. 인라인 스타일은 specificity `(1,0,0,0)`이므로 **모든 CSS 클래스보다 우선**한다.

```javascript
// GSAP이 적용하는 인라인 스타일
gsap.set(item, { opacity: 0, x: -20 });
// → element.style.opacity = "0"
// → element.style.transform = "translateX(-20px)"
```

이 때문에 GSAP으로 제어하는 속성(`opacity`, `transform`)은 Tailwind 클래스와 충돌하지 않는다. 문제가 되는 것은 **GSAP이 아닌 JavaScript로 CSS 클래스를 토글하는 경우**다. 이번 이슈가 정확히 이 케이스였다.

## 정리: Tailwind + 커스텀 CSS 혼용 시 원칙

1. **같은 CSS 속성을 Tailwind과 커스텀 CSS에서 동시에 제어하지 않는다.** 상태 변경이 필요한 속성은 한 곳에서만 관리한다.

2. **JavaScript로 상태를 토글할 때는 커스텀 CSS 클래스를 사용한다.** Tailwind 클래스를 직접 add/remove하면 다크모드 등 variant 조합이 복잡해진다.

3. **GSAP이 제어하는 속성은 Tailwind 클래스를 사용하지 않는다.** GSAP은 인라인 스타일로 동작하므로, Tailwind 클래스와 의도치 않게 겹치면 `gsap.set()`으로 초기화한 값이 GSAP 해제 후 Tailwind 값으로 돌아가는 문제가 생긴다.

4. **cascade 순서를 예측할 수 없으면 같은 관리 체계로 통일한다.** 빌드 도구가 CSS를 병합하는 순서는 설정에 따라 달라질 수 있으므로, 확실한 우선순위가 필요한 경우 같은 `<style>` 블록 내에서 관리하는 것이 안전하다.
