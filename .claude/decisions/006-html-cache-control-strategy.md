# ADR-006: HTML 파일 캐시 정책 — 브라우저/CDN 분리 전략

## 상태

승인됨

## 배경

master 브랜치에 push 후 GitHub Actions로 S3 배포 및 CloudFront 캐시 무효화가 실행되지만, 사용자가 페이지에 진입하면 새로고침을 해야만 업데이트된 콘텐츠가 보이는 문제가 발생했다.

기존 설정에서 HTML 파일에 `max-age=31536000` (1년)을 적용하고 있었다. CloudFront 캐시를 무효화해도 브라우저에 이미 캐싱된 HTML은 1년간 유지되어, 강제 새로고침 전까지 구버전이 표시되었다.

## 논의 내용

### HTML과 에셋의 캐싱 전략 차이

| 파일 유형 | 파일명 예시 | 특징 |
|-----------|-------------|------|
| JS/CSS (`_astro/`) | `index.D4kJ2x.js` | 파일명에 해시 포함 → 내용 변경 시 파일명도 변경 |
| HTML | `index.html` | 파일명 고정 → 내용 변경되어도 같은 URL |

에셋은 해시 기반 파일명으로 캐시 버스팅이 자동 처리되지만, HTML은 파일명이 고정되어 긴 캐싱 시 구버전 문제가 발생한다.

### 선택지 A: 짧은 max-age 적용

```
max-age=300, must-revalidate
```

- **장점:** 간단한 설정
- **단점:** 5분마다 오리진 요청 발생, CDN 캐싱 이점 감소

### 선택지 B: max-age=0, s-maxage 분리

```
max-age=0, s-maxage=31536000, must-revalidate
```

- **장점:** 브라우저는 매번 CDN에 요청하지만, CDN이 캐싱하여 빠른 응답. 배포 시 CloudFront Invalidation으로 즉시 업데이트 반영
- **단점:** 브라우저 로컬 캐시 미사용

### 선택지 C: 기존 유지 (max-age=31536000)

- **장점:** 최대 캐싱 성능
- **단점:** 배포 후 사용자가 새로고침해야 업데이트 확인 가능

## 결정

**선택지 B** — `max-age=0, s-maxage=31536000, must-revalidate` 적용

## 근거

- 브라우저는 매번 CloudFront에 요청하지만, CloudFront가 캐싱하고 있어 빠른 응답 제공
- 배포 시 CloudFront Invalidation 단계가 이미 워크플로우에 포함되어 있어, 무효화 후 즉시 새 버전 제공 가능
- HTML 파일은 용량이 작아 브라우저 로컬 캐싱 미사용의 성능 영향이 미미함
- 사용자 경험 개선: 새로고침 없이도 최신 콘텐츠 확인 가능

## 적용 범위

- `.github/workflows/deploy.yml` — HTML 파일 배포 단계의 `--cache-control` 값 수정
- 에셋(`_astro/*`) 및 기타 정적 파일의 캐시 정책은 기존 유지
